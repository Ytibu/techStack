# 01 表设计与数据类型

## 为什么业务表通常选择 InnoDB？

**面试回答：** 订单、库存、账户等业务需要多条修改一起成功或失败，还需要控制并发写冲突。InnoDB 支持事务、行级锁、崩溃恢复和 MVCC，更适合这类业务。MyISAM 不支持事务和行级锁，所以不能仅凭“读多写少”就选它。

存储引擎以表为单位选择。InnoDB 行锁能提高不同记录之间的并发度，但同一条热点记录仍然会串行竞争；换成 InnoDB 不意味着没有锁等待。

**追问：一条查询经过哪些环节？** 连接和权限检查后，服务层解析 SQL、优化执行计划，再通过执行器调用存储引擎访问数据。MySQL 8.0 已移除旧的查询缓存；InnoDB Buffer Pool 缓存数据页和索引页，不能混为一谈。

## 金额为什么用 DECIMAL，而不是 DOUBLE？

**面试回答：** `FLOAT`、`DOUBLE` 使用近似的浮点表示，金额计算需要明确的精度和舍入规则，通常用 `DECIMAL(p,s)`，Java 对应 `BigDecimal`。例如 `DECIMAL(12,2)` 的 12 是总有效位数，2 是小数位数，并不是整数可以存 12 位。

也可以用整数保存“分”，但需要统一单位，考虑溢出和不止两位小数的币种、费率等需求。数据库类型精确，不代表业务自动正确；折扣、税费、汇率的舍入时机必须统一。

**易错点：** Java 中从已有 `double` 构造 `BigDecimal` 可能带入误差，应优先从十进制字符串等精确输入构造。不能指望最后入库时再修正前面已经发生的误差。

## CHAR、VARCHAR、TEXT 怎么选？

**面试回答：** `CHAR` 适合长度稳定的短编码，`VARCHAR` 适合长度变化的短文本；正文等较大内容可以用 `TEXT`，并根据访问频率考虑拆到扩展表。类型选择要看实际长度、字符集、索引和查询方式，不能直接说 CHAR 一定更快。

`VARCHAR(100)` 的 100 通常表示最多 100 个字符，不是 100 字节。实际占用和可索引长度受字符集影响，`utf8mb4` 一个字符最多可占 4 字节，还要考虑行大小限制和长度元数据。

手机号、身份证号、订单号本质是标识，不参与算术，通常用字符串，避免丢失前导零，也兼容字母。字符集决定能存哪些字符，排序规则还决定大小写、重音等比较规则；业务唯一性也受它影响。

## DATETIME 和 TIMESTAMP 有什么业务差别？

**面试回答：** `TIMESTAMP` 写入和读取会按会话时区与 UTC 转换；`DATETIME` 保存的是日期时间字段值，本身不做这种时区转换。MySQL 8.0 中 TIMESTAMP 的日期范围明显更小，常说的 2038 年边界指这一类型，不是 DATETIME。

Java 的 `LocalDateTime` 没有时区信息，不应直接当成全球唯一时刻。跨时区业务应统一存储和连接时区约定，再明确映射成 `Instant`、带偏移时间或本地时间。仅仅把列改成 TIMESTAMP，不能消除 JDBC、会话时区和应用时区不一致的问题。

**业务追问：订单创建时间用什么？** 可以采用统一 UTC 约定的 DATETIME，也可以采用 TIMESTAMP，关键是范围、精度和全链路时区契约一致。不要把用户生日这类日期当成需要时区换算的时间点。

## 主键与业务唯一键为什么经常分开？

**面试回答：** 主键用于稳定地标识记录和组织聚簇索引，业务唯一键用于约束订单号、外部请求号等业务身份。内部主键通常选短、稳定、尽量有序的值，再为业务号建唯一索引，避免业务规则变动影响大量关联。

自增主键局部有序，通常有利于插入和索引空间；随机 UUID 较长、插入位置分散，可能增加页分裂与缓存压力。但有序写入也可能出现热点，跨库唯一性需要另行设计，不能宣称自增适合所有场景。

**追问：自增 ID 连续吗？** 不保证。事务回滚、插入失败或并发分配等都可能留下空洞；自增 ID 也不能严格代表事务提交顺序，因此不能用“最大 ID”直接认定最后提交的订单。

## NULL、默认值和唯一约束怎么设计？

**面试回答：** 先明确“未知”“未填写”和“空字符串”在业务上是否不同。确定必填的字段用 `NOT NULL`，合理默认值用于真实默认状态，不能为了避免 NULL 把所有未知金额都设成 0。数据库约束是并发场景下守住数据规则的最后一道保障。

MySQL 唯一索引允许多条记录在被索引列上取 NULL。因此用唯一键做幂等时，参与业务身份的列通常还应是 `NOT NULL`。唯一键也不是跨分片的天然全局约束。

**追问：逻辑删除后允许重新注册怎么办？** `UNIQUE(phone, deleted)` 只适合每个手机号最多保留一条相同 deleted 值记录的规则，反复删除重建可能冲突。需要先定义历史记录保留与有效记录唯一性，再选择独立历史表或经过设计的有效记录唯一约束，不能机械增加 deleted 字段。

## 外键、冗余字段与反范式怎么取舍？

**面试回答：** 外键能在数据库层保证引用完整性，但也增加写入检查和关联约束。单库业务可以使用；跨服务、跨库场景常通过业务流程维护关系，但必须补上校验、删除策略和异常修复，不能把“不用外键”理解为“不保证一致性”。

订单明细保存下单时的商品名称、成交价是业务快照，不能每次都关联商品当前价格。为读性能冗余用户名则是另一类取舍，需要说明用户名变化后是否同步、允许延迟多久、失败如何补偿。

**记忆句：** 表设计从业务含义、唯一性、访问路径和生命周期出发；类型越合适、约束越明确，后面越少依赖补救代码。
