# 2. 主从复制

## 2.1 概述

主从复制将主库产生的变更传播到从库，使多个实例按相应协议维护数据。常见用途包括分担读取、提供故障切换候选和分离某些管理负载，但复制本身不保证所有节点任意时刻都具有同样可读结果。

复制也不会自动替 Java 应用完成请求路由。数据传播是复制机制的职责，把哪些读写发往哪个节点则是访问层策略，需要分别理解。

## 2.2 基本过程

```text
主库产生 binlog 事件
    → 从库接收并记录到 relay log
    → 从库应用变更
    → 对应数据达到可读取状态
```

接收进度和应用进度是不同阶段。从库已经拿到日志，不代表修改已经应用成查询结果；使用并行应用等机制时，也要根据相应进度与提交规则判断，不能只看网络传输完成。

经典复制默认异步。主库可以在没有等待从库应用完成的情况下向客户端返回成功，因此主库故障后切到落后的从库，可能缺少已向调用者确认的事务。

## 复制确认方式

半同步在相关提交路径等待所需数量从库接收并持久记录事件的确认，改善特定故障下的传播保障。但确认并不要求从库已经应用事务，所以不能据此保证任意从库立即读到最新数据。

确认数量、等待点及超时退化会影响实际保证。半同步、普通异步和组复制等机制不是同一协议，不应只凭“有多副本”推导读写一致性或故障零丢失。[半同步复制](https://dev.mysql.com/doc/refman/8.0/en/replication-semisync.html)。

## 复制延迟

日志发送、从库接收和应用都可能形成延迟。网络、磁盘压力、从库能力、锁争用与大事务都会影响进度。长时间没有应用变化，不等于主库没有新业务写入。

延迟影响写后立即读、状态轮询、权限变化和故障切换。它与本机事务中的旧快照不同：一个是不同实例的数据进度，一个是当前事务的可见性规则。排查时还需要排除请求路由、缓存和条件错误。

## 故障切换的开发含义

切换不仅是更改连接地址，还涉及候选节点进度、旧主写入隔离、连接重建和调用结果确认。调用方可能在提交成功但响应丢失后重试，因此业务请求需要稳定身份和可查询结果，避免把“超时”直接当成“没有执行”。

本章不展开主从账户、配置文件和启动步骤。开发者需要掌握复制各阶段和失败边界，才能解释路由选择及其一致性承诺。
