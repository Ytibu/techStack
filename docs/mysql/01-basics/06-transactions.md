# 6. 事务

## 6.1 事务与业务边界

事务把一组操作作为一个提交或回滚单位。对 InnoDB，同一事务中的修改在成功提交后成为已提交结果；失败或主动回滚时按事务规则撤销。应用需要决定哪些修改必须一起完成，再确定事务范围。

事务边界通常与数据库连接相关，不与 Java 方法的文本边界天然重合。同一个业务方法如果使用多个不受同一事务管理的数据源，不能仅凭方法上有事务注解就认定全部操作属于同一本地事务。

外部 HTTP 调用、消息发送和支付请求不因本地数据库回滚而自动撤销。原子性应明确作用于哪些资源，跨资源一致性需要其他协议或恢复流程。

## 6.2 提交、回滚与自动提交

自动提交开启时，未显式开启事务的常规语句通常各自形成事务。显式开启后，后续修改在 COMMIT 或 ROLLBACK 等边界结束。SQL 执行成功与事务提交成功是不同阶段。

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

这只说明提交单位，不是完整转账实现。真实业务还要处理余额校验、影响行数、唯一请求号与异常回滚；将两条错误的更新放进事务并不会自动使它们符合业务规则。

ROLLBACK 也不是撤销任意已执行操作的通用命令。已经提交的事务、通常会隐式提交的 DDL、非事务引擎的相应修改，都不能按普通 InnoDB 事务修改统一理解。SAVEPOINT 可以提供事务内的部分回滚位置，但不产生一个独立已提交事务。

连接池复用连接时，需要确保事务与会话状态被正确处理。连接被长时间占用可能耗尽池资源；连接返回池并不等于调用者可以忽视未结束事务。

## 6.3 ACID

| 特性 | 含义与边界 |
| --- | --- |
| 原子性 | 事务范围内的修改整体提交或撤销，不保证事务之外的副作用一起撤销 |
| 一致性 | 事务前后应满足数据与业务不变量，需要约束和正确业务逻辑共同实现 |
| 隔离性 | 限制并发事务的相互影响，实际行为取决于隔离级别和访问方式 |
| 持久性 | 成功提交的数据在相应故障模型和持久化保证下可恢复 |

InnoDB 的回滚信息、日志、锁和多版本机制提供基础能力，不能把一致性简化为某两种日志的自动产物。例如两次并发业务请求即使都使用事务，仍可能因为不恰当的读后覆盖造成不符合预期的最终值。

## 6.4 并发事务问题

脏读是看到其他事务未提交的数据；不可重复读指同一事务中重读记录时看到其他事务已提交的变化；幻读关注相同条件下符合范围的记录集合受到其他事务插入等影响。

这些概念描述需要限制的并发现象，并不直接给出全部引擎实现细节。分析具体过程还必须说明普通读还是锁定读、是否有修改、事务何时建立读视图、使用什么索引。

“先读再写”也可能产生覆盖问题。两个事务依据同一个旧值各自计算，再不检查旧状态直接覆盖，可能丢掉其中一次业务更新。解决方向包括原子条件修改、版本校验或在正确事务中锁定相关记录。

## 6.5 事务隔离级别

| 级别 | 普通读取的典型理解 |
| --- | --- |
| READ UNCOMMITTED，RU | 允许观察未提交变化 |
| READ COMMITTED，RC | 每次一致性读取使用新的已提交视图 |
| REPEATABLE READ，RR | 通常复用事务首次一致性读建立的视图 |
| SERIALIZABLE | 施加更强的并发约束；显式事务中的普通读取通常采用共享锁定语义 |

InnoDB 的默认隔离级别是 RR，但项目中的连接设置可能改变它。级别越高通常约束越强，也可能增加等待和重试成本；选型不能只按“最高级最安全”判断。

RR 的普通快照读、锁定读与修改操作具有不同语义。重复快照读不直接看见别人后来提交的新行，范围锁定访问又可能通过间隙或临键锁限制插入；不能把标准现象表直接等同于所有 InnoDB 操作的实际行为。

在常见 Spring 本地事务中，还需注意代理调用、异常回滚规则及线程边界。默认代理模式下同类自调用不会额外触发被调方法的事务拦截；默认受检异常也不自动具有与 RuntimeException 相同的回滚规则，实际以项目配置为准。这属于应用怎样使用事务，不改变数据库事务本身的定义。
