# 04 联合索引与索引失效

## 联合索引为什么遵循最左前缀？

**面试回答：** `(a,b,c)` 按 a 排序，a 相同时再按 b、c 排序，因此通常可以高效定位 `(a)`、`(a,b)`、`(a,b,c)` 条件；缺少前面的列，后面列在整个索引中就不再连续有序，不能按相同方式直接定位。

最左前缀说的是索引列顺序，不是 WHERE 条件的书写顺序。`a = ? AND b = ?` 与 `b = ? AND a = ?` 通常不因书写先后改变可用索引前缀。

**边界：** 缺少 a 不等于“绝对不能使用这个索引”。可能出现索引全扫描、覆盖访问或满足条件时的跳跃扫描。要区分“是否访问索引”与“是否用联合前缀高效缩小范围”。

## 订单列表应该如何设计联合索引？

**面试回答：** 先明确常见查询的过滤、排序和返回列。例如按用户查某状态订单，再按创建时间和 id 倒序翻页，可考虑 `(user_id, status, created_at, id)`。前两列等值过滤，后两列服务排序及稳定分页；最后通过 EXPLAIN 和真实数据分布确认。

```sql
SELECT id, created_at, amount
FROM orders
WHERE user_id = ? AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

如果经常不带 status，`(user_id,status,created_at,id)` 不一定还能直接满足按 created_at 排序，需要评估另一种索引或访问方式。不能仅因为“status 区分度低”就断言它永远不能进入联合索引。

**取舍：** 多个等值列的相对顺序，还应考虑其他查询能否复用前缀、数据分布和排序需求，不是永远把单列区分度最高的列放第一。

## 遇到范围条件，后面的索引列一定失效吗？

**面试回答：** 对 `(a,b,c)`，`a = ? AND b > ? AND c = ?` 常见情况下先用 a、b 确定范围，c 不再继续像等值前缀那样收窄连续查找区间；但 c 仍可能参与索引下推、覆盖或过滤。因此“范围之后所有索引列完全失效”过于绝对。

`>`、`>=`、BETWEEN 等形成的区间边界可能不同，不能简单背“把 > 改成 >= 就全部恢复”。应看执行计划、实际扫描量和结果语义；不能为了走索引擅自改变业务条件。

## 哪些写法容易导致索引不能高效定位？

| 情况 | 为什么要注意 | 优先考虑 |
| --- | --- | --- |
| 对索引列做普通函数或计算 | 普通索引保存的是原值顺序 | 把计算移到常量侧，或单独设计函数索引 |
| 字符串列与数字参数比较 | 隐式转换可能破坏有效定位 | JDBC 参数类型与列类型保持一致 |
| `LIKE '%keyword'` | 左侧前缀不确定 | 确认是否需要专门的检索能力 |
| 联合索引跳过前导列 | 无法按通常的前缀方式定位 | 从高频查询重新评估索引顺序 |
| OR 的某个分支缺少有效访问路径 | 整体可能更适合全表扫描 | 评估分支索引或保持语义的改写 |
| 大部分记录都满足条件 | 索引回表成本可能高 | 接受合理全扫，或缩小业务返回范围 |

**易错点：** `!=`、`NOT IN`、`IS NULL` 并不必然导致完全不用索引。是否使用取决于可构造的范围、选择性和成本。全表扫描也不是唯一的“不够快”的原因。

## ORDER BY 一定要额外建立索引吗？

**面试回答：** 尽量让过滤与排序共享一个联合索引，例如固定 user_id 后，按 created_at、id 顺序扫描。排序列方向一致时，普通升序索引也可以反向扫描；混合方向需结合索引定义和版本能力判断。

如果过滤条件导致访问路径和排序顺序不一致，仍可能 filesort。`Using filesort` 表示没有直接按索引顺序得到结果，不意味着一定落盘，也不意味着这条 SQL 必须优化；要看排序数据量和耗时。

## 单列索引很多，能替代联合索引吗？

**面试回答：** 不一定。优化器可能选择其中一个索引，也可能进行 Index Merge，但多个单列索引不能自然提供联合索引的整体有序性。高频组合过滤与排序通常需要围绕查询设计联合索引。

增加 `(a,b)` 后，单列 `(a)` 可能冗余，但不能不检查唯一性、其他查询、索引宽度就直接删除。每个索引都应该能解释服务哪类查询，以及写入成本是否值得。
