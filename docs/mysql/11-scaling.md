# 11 读写分离与分库分表

本篇只保留影响 Java 业务设计的内容，不涉及主从部署、MyCat 安装或配置。

## 主从复制的基本链路是什么？

**面试回答：** 主库产生 binlog，从库接收后写入 relay log，再由应用线程执行变更。经典复制默认异步，主库成功并不代表从库已经接收并应用，读从库可能看到旧数据。

复制是持续传播变化的机制，读写分离是把业务请求路由到不同节点的策略。二者经常配合，但不是一个概念；只建立复制关系不会自动替 Java 应用完成读请求路由。

## 下单成功后查不到订单，怎么解释和处理？

**面试回答：** 如果写主库、随后读从库，复制延迟可能造成“刚写完就查不到”。先确认请求路由与复制进度，区分这类旧读和事务回滚、错误参数、缓存旧值等问题。

| 处理方式 | 适用情况与代价 |
| --- | --- |
| 写后关键查询走主库 | 简单直接，但增加主库读负载 |
| 事务内读写绑定同一主库连接 | 适合同一事务内的一致性，路由必须在取得连接前正确确定 |
| 按复制位点/GTID 等待从库追上 | 需要可用的进度机制与等待上限，超时后回退 |
| 允许延迟的列表走从库 | 接受最终一致性，并在交互上定义何时可见 |

固定“写后五秒内读主库”只是经验窗口，不能证明五秒后一定同步完成。必须说明延迟异常时如何回退，以及哪些业务不能接受旧读。

## 半同步复制能保证从库立刻查到新数据吗？

**面试回答：** 不能。半同步等待所需数量的从库接收并持久记录事务事件，但收到日志不等于已应用成可查询数据。它改善的是特定故障场景下的复制确认保障，不自动提供任意从库的读后写一致性。

确认数量、等待点、超时退化等都会影响实际保证。普通异步复制、半同步复制和组复制等机制不能混为一谈；面试只需清楚说明自己讨论的前提。

## 复制延迟对业务有什么影响？

**面试回答：** 会影响写后立即读、状态轮询、权限变更、库存展示和故障切换的数据完整性。大事务、从库应用能力不足或争用等可能放大延迟，不能只把问题归因于网络慢。

读写分离适合把允许一定延迟的读取分担出去，不能缓解所有主库写热点。主库故障切换也不只是“把连接换到从库”，还要确认复制进度、旧主写入隔离和客户端重试幂等。

## 什么情况下才考虑分库分表？

**面试回答：** 先用监测确认容量、I/O、CPU、热点或维护窗口已经成为瓶颈，再评估索引、SQL、冷热分离、归档和读写分离等较低成本方案。没有一个脱离行宽、索引和负载的“达到某个固定行数就必须分表”标准。

分表把单表的数据拆小，但同实例内分表不自动增加主机资源。分库能分散实例负载，也引入跨库事务、全局查询和运维复杂度，必须有收益依据。

## 垂直拆分与水平拆分有什么区别？

**面试回答：** 垂直拆分按业务或字段划分，例如订单与用户分库、订单大字段拆扩展表；水平拆分按相同结构把不同行分散到多个分片。前者主要调整职责和访问宽度，后者主要分摊数据与访问规模。

垂直拆分可能增加关联或跨服务调用，水平拆分需要路由规则。两者都会改变事务和查询边界，不能只说明“每张表变小了”。

## 分片键怎么选？取模和范围怎么取舍？

**面试回答：** 选择高频查询可携带、分布相对均衡且尽量稳定的业务键。例如按 user_id 分片，用户订单列表容易路由；但按订单号查详情就需要订单号携带路由信息或额外映射。多租户中单个超大租户也可能成为热点。

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 哈希/取模 | 分布通常相对均匀 | 扩容可能迁移大量数据，范围查询易跨分片 |
| 时间/数值范围 | 范围路由和归档直观 | 新数据可能集中到热点分片 |

一致性哈希等策略可以减少某些扩容迁移，但不能自动消除数据迁移、一致性校验和业务热点。需要说明扩容期间如何路由与避免重复或遗漏。

## 分库分表给 Java 业务带来哪些代价？

**面试回答：** 至少有跨分片 JOIN、全局排序分页、全局唯一性、分布式事务、扩容迁移与路由维护。单库本地唯一索引只约束所在分片，跨库操作也不再天然属于一个本地事务。

全局分页往往需要从多个分片取候选结果再归并，深分页代价更高；按分片键定向查询通常更便宜。全局唯一 ID 也不等于自动具备任意业务唯一性，例如“同一用户只能有一条有效订阅”还要看规则是否落在同一分片或另有协调机制。

**记忆句：** 读写分离主要分担读压力，分片分散数据与负载，两者都要付出一致性或查询复杂度的成本。
