# 09 库存、幂等与业务一致性

本篇把 PDF 中的事务、约束、索引和锁组合为面试业务回答；下列方案是业务补充，不是完整项目案例。

## 高并发扣库存，怎么避免超卖？

**面试回答：** 不要先普通查询库存，再把 Java 中算出的值无条件写回。可以把校验和扣减放进一条原子条件更新，数据库在并发写控制下判断库存是否足够；检查影响行数，决定成功或失败。

```sql
UPDATE inventory
SET stock = stock - ?
WHERE sku_id = ? AND stock >= ?;
```

要求扣减数量为正数、两个数量参数一致，且 sku_id 有符合业务唯一性的索引。影响 1 行代表成功；0 行可能表示库存不足或记录不存在，需要按接口约定解释，不能直接当成数据库故障。

如果扣库存和创建订单都在同一个 MySQL 事务资源里，应放进一个事务；订单写入失败时回滚库存扣减。跨服务库存和订单不能仅靠一个本地事务获得整体原子性，需要另外设计状态与补偿。

**追问：热门商品单行竞争怎么办？** 原子 SQL 能保证正确性，但热点行仍然串行争用。可根据业务考虑排队、限流、库存分桶等方案，同时解释分配、汇总与一致性的额外复杂度。

## 乐观锁与悲观锁怎么选？

**面试回答：** 悲观方案先锁定记录，再执行依赖它的判断和修改，适合冲突较多、必须串行检查的短事务。乐观方案在更新时校验版本或旧状态，冲突时返回失败或重新读取，适合冲突较少、能够接受重试的场景。

```sql
UPDATE products
SET price = ?, version = version + 1
WHERE id = ? AND version = ?;
```

版本不匹配时影响 0 行，应用不能忽略并继续按成功处理；也不应不设上限地重试。乐观锁不是数据库完全不加锁，最终 UPDATE 仍有数据库写锁，只是应用不提前长期持有读取锁。

对简单扣减，带库存条件的原子 UPDATE 往往比“读版本再写版本”直接；对需要比较多个字段的编辑提交，版本号通常更容易表达“拒绝覆盖他人修改”。

## 如何避免订单重复创建？为什么先查后插不够？

**面试回答：** 先查不存在再插入有并发窗口，两个请求都可能查到不存在。应为业务请求号建立合适的非空唯一约束，通过插入竞争由数据库裁决；冲突后按幂等规则查询已有结果。

幂等键要明确作用域，例如 `(merchant_id, request_id)`。重复请求还应核对金额、商品等关键参数；相同请求号携带不同业务内容不能直接返回原成功结果。

**事务边界：** 请求记录与实际业务写入尽量在同一事务中提交，避免只占用了幂等键却没有业务结果。需要区分处理中、成功、失败和可重试状态，唯一索引解决“不能重复插入”，状态机解决“重复请求该返回什么”。

## 支付回调重复或乱序，怎么保证订单只生效一次？

**面试回答：** 使用外部支付流水唯一约束防止重复入账，再用状态条件更新限制合法迁移，例如只允许 CREATED 变成 PAID。记录流水、更新订单和本地账务等需要一起生效的数据库修改放在同一个事务内。

```sql
UPDATE orders
SET status = 'PAID', paid_at = ?
WHERE id = ? AND status = 'CREATED';
```

影响 0 行不能直接认定已经支付成功；还可能已取消、订单不存在或处于其他状态，需要读取并核对支付流水。退款、撤销也应有独立合法迁移规则，不能让晚到的“支付成功”覆盖已退款状态。

**关键边界：** 唯一约束、状态条件和事务需要组合使用；只在 Java 中判断状态，或者只给接口加 synchronized，都无法覆盖多实例并发与进程重启。

## 本地事务提交了，消息没发出去怎么办？

**面试回答：** 一种常见做法是本地事务中同时写业务记录和待发送事件记录（Outbox）。提交后由可靠的投递过程发送，失败重试，成功后更新投递状态。这样至少保留了“还有消息需要发送”的持久事实。

发送成功后进程可能来不及更新状态，因此仍会重复发送；消费者需要按事件 ID 幂等处理。业务修改与消费去重记录也应尽量在同一消费事务内提交。

**追问：事务提交后回调发送够吗？** 仅内存回调存在“数据库提交后、消息发送前进程退出”的窗口，不能提供可靠补发。数据库内部 redo/binlog 的两阶段提交，也不自动解决 MySQL 与 MQ 的双写问题。

## MySQL 和 Redis 缓存如何保持一致？

**面试回答：** 常见 Cache Aside 做法是读时先查缓存，未命中再查数据库并回填；更新先提交数据库，再使缓存失效。数据库作为事实来源，缓存允许什么程度的延迟，需要提前定义。

数据库成功、删缓存失败时，需要有可靠重试或变更订阅等补偿路径，TTL 只能限制一部分陈旧持续时间。并发读可能把旧数据回填到已经被删除的缓存中，因此“先更新库再删缓存”也不等于强一致。

对强一致要求高的扣款判断，不应依赖可能过期的缓存余额做最终裁决。可以让关键判断走数据库条件更新，缓存服务展示；延迟双删只是特定时序下的缓解，不能证明所有竞争窗口都被关闭。

## 请求超时了，能直接重试扣款吗？

**面试回答：** 超时代表客户端没有及时得到结果，不能证明数据库没有提交。应该使用稳定的业务请求号做幂等，并查询请求结果；无法确认时进入对账或查询流程，不能换一个新请求号直接再扣一次。

连接断开、应用崩溃和 COMMIT 响应丢失，都可能让客户端处于“结果未知”。事务原子性解决数据库内部全成或全败，幂等与结果查询解决调用者如何安全恢复。

**记忆句：** 约束守住唯一性，条件更新守住状态与数量，事务守住本地原子性，幂等和补偿处理重试与跨系统故障。
