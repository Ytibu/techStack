# 05 慢 SQL 排查与分页优化

## 接口突然变慢，为什么不能先加索引？

**面试回答：** 先确认慢在哪里，再改数据库。接口耗时可能来自连接池等待、SQL 执行、锁等待、网络、结果映射或下游调用。应结合链路耗时和实际 SQL，把参数、调用次数、扫描行数、返回行数和执行计划对应起来。

排查顺序可以这样复述：

1. 找出贡献主要耗时的 SQL 和调用次数，确认是否出现 N+1 查询。
2. 区分等待连接、等待锁、真正执行慢、返回数据过多。
3. 查看实际参数下的执行计划、索引、数据分布与扫描量。
4. 根据原因减少扫描、回表、排序、调用次数或事务持锁时间。
5. 比较修改前后的耗时、资源消耗和业务结果，检查写入代价。

慢查询日志能提供数据库侧线索，但不是接口耗时的全部。不能只把日志阈值当成业务接口的合格线。

## EXPLAIN 重点看哪些字段？

**面试回答：** 重点看访问哪张表、使用哪个索引、预计扫描多少行、如何过滤、是否额外排序或使用临时表，再结合多表连接顺序判断成本。不能只盯着 key 是否非空。

| 字段 | 面试中怎么解释 |
| --- | --- |
| `type` | 访问方式；const、eq_ref、ref、range 通常有较强定位能力，index 是全索引扫描，ALL 是全表扫描 |
| `possible_keys` / `key` | 候选索引与最终选择的索引，不保证候选索引都会被使用 |
| `key_len` | 参与访问的索引键最大长度线索，受类型、字符集和 NULL 等影响 |
| `rows` / `filtered` | 估计扫描行数和过滤比例；估计不等于实际 |
| `Extra` | 覆盖访问、索引下推、排序、临时表等补充信息 |

`Using index` 通常表示覆盖访问；`Using index condition` 表示 ICP；`Using filesort` 表示需要额外排序；`Using temporary` 表示使用内部临时表，不能据此认定一定落盘。

**追问：EXPLAIN ANALYZE 呢？** MySQL 8.0.18 起提供，它会真正执行支持的语句并展示实际执行信息。适合对比估计与实际行数、循环次数和耗时；使用前要评估执行开销，不能当成纯静态分析。

## SQL 用了索引为什么还慢？

**面试回答：** 索引只是访问方式，还可能扫描过多候选记录、反复回表、排序聚合大量结果，或者被锁阻塞。同一条 SQL 还可能因为参数选择性不同、统计估计不准、缓存冷热或并发负载而表现不同。

例如低选择性的状态条件命中大部分订单，用二级索引再取整行并不一定划算。业务上能否增加时间范围、用户范围、只取必要列，往往比强制走索引更有价值。

**易错点：** `FORCE INDEX` 是具体问题下的控制手段，不是慢 SQL 的默认答案。数据分布变化后，强制路径也可能退化。

## 深分页为什么慢？

**面试回答：** `LIMIT offset, size` 通常仍需访问并跳过前面的结果。offset 越大，丢弃的记录越多；若还需要回表或排序，成本更高。索引可以降低单条访问成本，却不能自动消除跳过 offset 的工作。

方案一是延迟关联：先用较窄、可覆盖的索引找出本页主键，再查询本页完整数据，减少大量无效回表。它仍然要跳过前面的索引项，所以不能说已经从根本上消除了深分页。

方案二是游标分页：下一页从上一页最后一个排序键继续，适合连续翻页和滚动加载。

```sql
SELECT id, created_at, amount
FROM orders
WHERE user_id = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这里以 `(created_at,id)` 作为稳定游标，两个时间参数来自同一条末尾记录；可评估 `(user_id,created_at,id)` 索引。实际是否高效仍要检查范围计划。

**业务边界：** 游标分页不擅长任意跳转第 N 页。排序字段最好稳定，若翻页期间记录被修改或删除，仍需定义允许的重复、遗漏和一致性范围。只按不唯一的 created_at 排序，容易出现不稳定分页。

## ORDER BY、GROUP BY 和大批量操作怎么优化？

**面试回答：** 优先减少参与排序和聚合的行，利用合理的联合索引，避免取不必要的大字段。排序少量结果即使用 filesort 也可能足够快，应以实际成本决定是否增加索引。

批量写入能减少网络与提交开销，但单次事务不能无限大。按可控批次提交，评估持锁时间、日志量、失败重试与复制延迟。批量删除也要限制范围并使用合适的定位条件，避免一次锁住大量业务记录。

## Java 侧还有哪些常见性能问题？

**面试回答：** 常见的是循环中逐条查库、查询返回过多字段、无界列表、大 IN 列表，以及连接长时间被事务占用。可以在清楚数据量和语义后批量查询、按业务分批、按需返回字段。

连接池耗尽时盲目增大池子，会把压力转移到数据库。先检查慢事务、连接泄漏、SQL 耗时和并发需求；“数据库连接数更多”不等于吞吐一定更高。
