# 10 日志、提交与数据可靠性

## redo、undo、binlog 怎么区分？

**面试回答：** redo 支持 InnoDB 崩溃后重做恢复，undo 支持事务回滚和历史版本读取，binlog 记录服务器层的数据变更事件，用于复制与基于日志的恢复。它们解决的问题不同，不能相互替代。

| 日志 | 核心用途 | 面试关键词 |
| --- | --- | --- |
| redo log | 恢复已记录的页修改，支持持久性 | InnoDB、WAL、崩溃恢复 |
| undo log | 撤销修改、重建旧版本 | 原子性、版本链、MVCC |
| binlog | 传播和重放已记录的数据变更事件 | 服务器层、复制、恢复、变更订阅 |
| 慢查询日志 | 分析耗时 SQL | 性能线索，不是事务恢复机制 |

面试可以把 redo 理解为记录页修改的信息，undo 理解为恢复旧状态所需的信息，但不必把 undo 说成“原 SQL 的反向 SQL 文本”，实际是引擎内部的回滚信息。

## 为什么提交时不把所有数据页直接写回磁盘？

**面试回答：** 业务修改可能分布在多个数据页，逐页同步落盘会产生较重的随机 I/O。WAL 让相关日志先满足持久化要求，数据页可以之后再刷盘；崩溃后根据日志恢复。顺序追加日志和批量刷脏页通常更有利于吞吐。

数据页还没写回磁盘，不等于事务没有持久性；真正要看恢复所需日志是否已经满足持久化保证。相反，内存中改成功也不等于提交成功。

## redo 为什么不能代替 binlog？

**面试回答：** redo 面向 InnoDB 内部恢复，并会随着检查点推进复用相应空间，不是长期保存所有业务历史的归档日志。binlog 面向服务器层的数据变更传播，承担复制和时间点恢复等用途。两套日志需要在提交协议中协调一致。

binlog 也不是“把所有 SQL 原样保存一份”。普通 SELECT 通常不记录，ROW 格式主要记录行变更事件；不同格式、事务与非事务操作有各自语义。

## 数据库内部两阶段提交解决什么问题？

**面试回答：** 开启 binlog、使用 InnoDB 的常见提交路径中，需要协调引擎事务和 binlog，避免恢复后“数据库里有这笔修改但复制日志里没有”，或相反。可以用 redo prepare、写入 binlog、引擎 commit 的框架理解，再通过事务标识在崩溃恢复时判断提交结果。

这是简化理解，真实实现还包含组提交和不同持久化阶段。不能把这几个词背成所有版本下逐条独立 fsync 的固定顺序，也不能把 MySQL 内部协调直接等同于跨服务分布式事务。

## 返回提交成功后一定不会丢吗？

**面试回答：** 需要说明故障类型和持久化设置。常见强持久化配置是 `innodb_flush_log_at_trx_commit = 1` 配合 `sync_binlog = 1`，使提交路径上的 redo 和 binlog 按相应策略同步。但仍依赖操作系统、磁盘和存储正确兑现同步语义。

降低同步频率可以提升某些负载下的吞吐，但在进程、系统或电源故障中存在不同程度的数据丢失窗口。不能把“通常一秒刷一次”说成严格最大只丢一秒，也不能拿异步从库直接证明主库已提交事务必然被完整保留。

**业务边界：** 支付等业务还需要外部流水、对账和幂等。数据库日志保证是系统可靠性的一层，不替代端到端确认。

## binlog 的 ROW、STATEMENT、MIXED 有什么区别？

**面试回答：** MySQL 8.0 支持这些格式。STATEMENT 以语句为主要记录形式，某些不确定性语句会让重放一致性更复杂；ROW 记录行变更，便于更明确地复制行结果，但大批量修改可能带来较大日志量；MIXED 根据情况切换。

对于变更订阅与缓存更新，ROW 形式常便于获得行事件，但具体有哪些前后镜像还受配置等影响。不能假定每条事件都包含任意业务需要的全部字段。

格式支持、默认值与弃用状态会随版本变化；本篇以 PDF 所用的 MySQL 8.0 语境解释，不把其格式选项直接推广到后续所有版本。

## 误删数据时，为什么通常要有备份加日志？

**面试回答：** 常规时间点恢复需要一个有效的数据基线，再按 binlog 等恢复到目标时刻。只有部分日志、缺少基线和完整范围，通常不能凭空重建全部数据。redo 也不是给业务人员直接撤销误删的按钮。

面试重点是说明恢复能力需要事先保留有效基线与变更历史，以及误删可能通过复制传播；从库本身不等同于独立备份。具体备份、部署和恢复命令不属于本知识库范围。
