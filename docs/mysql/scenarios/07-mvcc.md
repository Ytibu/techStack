# 07 MVCC 与快照读

## 什么是 MVCC？它解决什么问题？

**面试回答：** MVCC 是多版本并发控制。InnoDB 通过记录版本信息、undo 历史版本和 ReadView，让普通一致性读找到对当前事务可见的版本，减少读写之间的阻塞。它让读取旧版本成为可能，但不替代写操作之间的锁。

例如用户查询订单时，不必为了看一个已提交的版本一直等待另一个事务修改同一订单；但两个事务同时扣同一条库存，仍需要协调写冲突。

## 快照读与当前读怎么区分？

| 读方式 | 常见语句 | 读取与并发特点 |
| --- | --- | --- |
| 快照读 | RC/RR 下的普通 SELECT | 读取可见版本，通常不对读取行加记录锁 |
| 锁定读 | SELECT ... FOR UPDATE / FOR SHARE | 依据当前记录读取并加锁，可能等待冲突事务 |
| 修改操作 | UPDATE、DELETE 等 | 按当前记录和加锁规则处理修改，不在旧快照上覆盖历史 |

**面试回答：** 当前读不是“可以读到别人没提交的数据”。遇到冲突锁仍然需要等待；关键是它不受之前普通一致性读的旧快照限制。

普通 SELECT 不加记录锁，也不代表完全没有任何锁或等待。例如访问表需要元数据锁，碰到 DDL 仍可能等待。

## 版本链与 ReadView 怎么配合？

**面试回答：** 记录保存最近修改事务的信息和回滚指针。修改产生的 undo 可以帮助重建旧版本；读取时根据 ReadView 判断当前版本是否可见，不可见就沿版本链寻找更早的可见版本。ReadView 是可见性规则的视图，不是把整张表复制一份。

最关键的可见性规则可以按含义记忆：

- 自己的修改可以看见。
- 在视图建立前已经提交的版本通常可见。
- 视图建立时仍活跃的其他事务版本不可见，即使它之后提交，也不改变旧视图。
- 视图建立之后才获得对应修改事务 ID 的版本不可见。

若被追问边界值，可以解释：版本事务 ID 小于活跃 ID 下界时可见；大于等于当时“下一个将分配的事务 ID”上界时不可见；中间区间再检查是否属于活跃事务集合。不要机械背原资料中把上界写成严格大于的简化表格。

## 用一个时间线解释 RC 和 RR

假设订单状态最初是 `CREATED`，事务 A 使用普通一致性读，事务 B 修改状态后提交。

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| T1 | 开启事务并首次查询，读到 CREATED | |
| T2 | | 改为 PAID 并提交 |
| T3 | 再次普通查询 | |

**面试回答：** RC 在 T3 建立新的语句级视图，可以读到 PAID；RR 复用 T1 的视图，仍读到 CREATED。如果 T3 换成 SELECT FOR UPDATE，则不再沿用旧的普通读快照，会按锁定读规则读取当前记录。

这个差别解释了“为什么事务里重复查询还是旧状态”。但如果 A 自己修改了记录，后续普通读可以看到自己的修改，不能说 RR 永远展示事务开始时的一切。

## RR 到底有没有解决幻读？

**面试回答：** 必须限定读方式。RR 的一致性快照读复用同一视图，重复范围读取不会因为别人之后提交的插入而直接看到新行；范围锁定读通过 next-key/gap 等锁限制相关间隙插入。两者分别解决不同读取方式下的问题，不能简单说“只靠 MVCC”或“RR 一定完全没有任何幻读相关现象”。

混用快照读和当前读时，可能观察到旧快照外的数据；事务自身修改某些原先不可见的行后，也可能改变后续可见结果。需要防止业务范围内出现新记录时，应设计约束或正确的范围锁定流程，不能仅凭默认 RR 认为“查无此订单”就能安全插入唯一业务订单。

## undo 会在提交后立刻删除吗？

**面试回答：** 不一定。某些更新、删除产生的历史版本还可能被其他事务的读视图使用，需要等不再被需要后才能清理。长时间保留读视图会阻碍旧版本回收，这也是长事务的成本之一。

MVCC 没有复制整库，但仍然要付出历史版本空间、可见性判断和清理成本。读写不互相阻塞的优势，并不意味着历史版本可以无限保留。
