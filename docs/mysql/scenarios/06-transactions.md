# 06 事务与隔离级别

## 如何结合订单业务解释 ACID？

**面试回答：** 以创建订单和扣库存为例，原子性要求同一事务内的修改一起成功或失败；一致性要求事务前后满足库存非负等业务规则；隔离性限制并发事务之间的干扰；持久性要求已成功提交的数据在约定的故障与持久化保证下可以恢复。

InnoDB 通过 undo 支持回滚，通过 redo 等机制支持崩溃恢复，通过锁与 MVCC 实现不同程度的隔离。但业务一致性还需要正确的 SQL、约束和事务边界，不能说加了事务就自动保证所有业务规则。

## 脏读、不可重复读、幻读有什么区别？

| 问题 | 业务理解 |
| --- | --- |
| 脏读 | 读到另一个事务尚未提交的变更，对方回滚后该值不成立 |
| 不可重复读 | 同一事务两次读取同一记录，看到其他事务已提交的修改或删除 |
| 幻读 | 对同一范围进行重复读取，其他事务提交的插入等改变了符合条件的记录集合 |

**面试回答：** 不可重复读主要看同一记录的值变化，幻读主要看满足条件的记录集合变化。解决问题时必须说明隔离级别和读方式，不能只背一个现象表就推导所有 InnoDB 行为。

## 四个隔离级别怎么回答？

**面试回答：** 读未提交允许脏读；读已提交让普通一致性读看到语句级已提交快照；可重复读在同一事务内通常复用首次一致性读的快照；串行化施加更强的并发限制，以更多等待和较低并发度换取更强隔离。InnoDB 默认是可重复读，但应用实际设置仍要确认。

| 隔离级别 | 普通读的关键特征 | 业务取舍 |
| --- | --- | --- |
| RU，读未提交 | 可能读到未提交值 | 很少用于需要可信业务读取的场景 |
| RC，读已提交 | 每次一致性读建立新快照 | 同一事务中允许看到别人刚提交的数据 |
| RR，可重复读 | 通常复用首次一致性读快照 | 稳定读取同一数据视图，部分锁定范围更大 |
| Serializable，串行化 | 显式事务中普通 SELECT 通常转换为共享锁定读 | 冲突、等待和重试成本更高 |

提高隔离级别不必然解决业务并发错误。比如先读库存再把计算结果覆盖写回，即使默认 RR 也需要明确的并发控制。

## RR 的快照在 BEGIN 时就生成了吗？

**面试回答：** 通常不是。普通 `START TRANSACTION` 或 BEGIN 开启事务后，RR 的快照通常在第一次一致性读时建立。`START TRANSACTION WITH CONSISTENT SNAPSHOT` 在适用隔离级别下显式请求立即建立一致性快照，是需要区分的例外。

如果只写 BEGIN，随后其他事务提交，再进行第一次普通 SELECT，这次读取可能包含对方的新提交。Java 方法开始执行的时间也不等于数据库快照已经建立的时间。

## 为什么事务里查到旧值，UPDATE 却能改新值？

**面试回答：** 普通 SELECT 在 RC/RR 下通常是一致性快照读；UPDATE、DELETE 和 SELECT FOR UPDATE 属于需要锁定或基于当前记录处理的操作。RR 不会让写操作只在历史快照上修改，因此读写混合时要区分两种语义。

如果业务要基于读取值再修改，可以在同一事务内锁定读取，或用条件更新、版本号校验，而不是把普通快照读的结果当成已经被锁住的事实。

## 为什么要避免长事务？

**面试回答：** 长事务可能长时间占用连接和锁，保留旧读视图还会延缓历史版本清理，增加 undo 压力。它也扩大失败回滚和锁冲突的影响范围。事务只包住必须原子完成的数据库修改，外部 HTTP、用户等待和耗时计算尽量移出持锁阶段。

拆小事务也有代价：原来整体原子的操作会变成分段提交，需要定义部分成功、重试和补偿。不能为了性能把必须一起提交的数据随意拆开。

## Java 的 @Transactional 代表什么边界？

**面试回答：** 在常见的 Spring 代理模式和本地 JDBC 事务管理下，它通过代理管理事务入口，并把事务关联到当前执行线程中的数据库资源。要确认调用经过代理、使用预期的数据源和事务管理器，方法中的 SQL 才能进入预期事务。

默认配置下 RuntimeException 和 Error 会触发回滚，受检异常通常不会；可以按业务配置 rollbackFor 等规则。Spring 新版也提供调整全局默认规则的能力，因此应说明项目配置，不能把默认行为说成不可修改。

常见问题包括同类内部自调用绕过代理、异常被捕获后正常返回、方法切换线程，以及操作了不在同一事务资源中的数据库。`readOnly = true` 通常是事务提示和优化意图，不能当成业务权限隔离保证。

**业务边界：** 普通本地事务不会自动回滚已经完成的外部支付调用，也不会自动把两套独立数据库或消息系统绑定成一个原子提交。相关方案见 [业务并发与一致性](./09-business-consistency)。
