# 08 锁、死锁与锁等待

## 行锁、间隙锁、临键锁分别锁什么？

**面试回答：** InnoDB 的记录锁锁定索引记录，间隙锁限制向索引记录之间的间隙插入，临键锁是记录锁和其前面间隙锁的组合。RR 下范围锁定访问常用临键锁防止相关范围出现新行，但实际范围还取决于索引、条件和执行路径。

| 锁 | 业务影响 |
| --- | --- |
| Record Lock | 限制其他事务冲突地修改或锁定同一索引记录 |
| Gap Lock | 阻止向相关间隙插入；本身不表示锁住现存记录 |
| Next-Key Lock | 同时约束记录及其前间隙，用于范围并发控制 |

唯一索引完整等值命中已存在记录时，通常只需要记录锁；查找不存在的值时，RR 下可能涉及间隙锁。非唯一等值和范围访问可能锁到多条记录及间隙，不能说 WHERE 最后只匹配一行就只锁一行。

**追问：RC 没有间隙锁吗？** RC 对一般搜索与索引扫描禁用间隙锁，但外键检查、重复键检查等仍存在例外。不要背成“RC 绝对不会有间隙相关锁”。

## 共享锁与排他锁怎么理解？

**面试回答：** 同一记录的共享锁彼此兼容，排他锁与其他事务的共享、排他记录锁冲突。SELECT FOR SHARE 常用于共享锁定读，SELECT FOR UPDATE 用于排他锁定读。事务结束后相应事务锁释放。

普通快照 SELECT 一般不申请记录共享锁，所以“排他记录锁阻塞所有读取”不准确。锁定读、普通一致性读和显式表锁必须分开讨论。

意向锁属于表级协调信息，用来表明事务将在表内使用共享或排他行锁，帮助表级锁判断冲突。看到 IX 不代表整张表的所有行都不能被其他事务更新。

## FOR UPDATE 为什么要放在事务里？

**面试回答：** 如果要保证“读后再修改”期间不被并发冲突操作穿插，锁定读取和修改必须在同一个有效事务、同一事务资源中完成。自动提交的一条 SELECT 执行完即结束事务，不能保护后续另一个事务中的修改。

```sql
START TRANSACTION;
SELECT balance FROM accounts WHERE id = ? FOR UPDATE;
-- 在同一事务内校验并更新余额
UPDATE accounts SET balance = balance - ? WHERE id = ?;
COMMIT;
```

这只表达锁定流程。实际业务还要校验余额、异常回滚和请求幂等。单条带条件的原子 UPDATE 可能更简单，见 [业务并发与一致性](./09-business-consistency)。

## 无索引 UPDATE 会把行锁升级为表锁吗？

**面试回答：** 不应这样表述。InnoDB 没有“因为没走索引就自动把行锁升级成表锁”的常规锁升级机制。缺少合适索引时会扫描并锁定大量索引记录；RR 下还可能涉及广泛的间隙，看起来影响了整表，但原因是访问和加锁范围扩大。

索引既影响速度，也影响锁覆盖范围。RC 与 RR 对非匹配记录锁的释放、间隙处理不同；分析具体 SQL 时，要看执行路径和实际锁信息，不能只依据最终影响行数。

## 死锁与锁等待超时有什么不同？

**面试回答：** 普通锁等待是等待对方释放资源；死锁是多个事务形成循环依赖。比如 A 先锁账户 1 再锁账户 2，B 反过来锁，双方都无法继续。InnoDB 开启死锁检测时通常会选择一个事务回滚来打破环路，应用仍要处理失败。

| 情况 | 常见错误 | 处理重点 |
| --- | --- | --- |
| 死锁 | 1213 / SQLSTATE 40001 | 确认整个事务已失败，按业务幂等规则有限重试整个事务 |
| 锁等待超时 | 1205 | 默认通常回滚当前语句，事务是否整体回滚还受配置和框架处理影响 |

**易错点：** 超时后捕获异常、继续执行剩余步骤并提交，可能留下部分业务修改。应明确回滚事务后再决定是否重试，不能只重放最后一条 SQL。

## 如何减少死锁，业务代码怎么兜底？

**面试回答：** 多个资源按统一顺序加锁，缩短事务，给定位条件建立合适索引，控制批量规模，避免持锁时调用外部服务。死锁仍可能发生，需要收集死锁信息，并对可重试事务设置次数上限、退避和幂等保障。

不能无限重试，也不能对已经发生外部副作用的流程盲目重放。比如转账事务失败可以整体重试，但已经发出的支付请求必须通过业务请求号识别和查询结果。

## 没有更新同一行，为什么也会互相等待？

**面试回答：** 可能竞争同一范围的间隙、唯一键检查、外键检查，也可能在等待元数据锁。长事务访问过一张表，会影响需要冲突 MDL 的结构变更；排队的 DDL 又可能扩大后续请求等待。

排查时区分记录锁、间隙锁、MDL 和连接等待。可以结合事务信息、`performance_schema.data_locks`、`data_lock_waits`、`metadata_locks` 以及死锁报告找出持锁者和等待链。先定位原因，再决定缩短事务、调整查询或协调变更。
