# 2.7 索引设计原则

## 从查询集合确定索引

索引应对应具体访问需求。先整理高频和高成本查询的过滤条件、排序方式、返回列、分页行为，再寻找可以共享的访问前缀。单独分析一个 SQL 可能得到过多索引，忽略其他查询又可能错误删除仍有价值的结构。

等值条件常适合组成前导部分，之后结合范围和排序设计。多个等值列的先后还需考虑前缀复用、不同参数的匹配比例，以及某些条件是否经常缺省。列出索引时应能说明每一列为何放在这个位置。

区分度反映列值区分记录的能力，是重要依据，但不是唯一规则。状态列可能单独选择性低，却在固定用户、租户或其他条件后缩小范围；也可能为了排序前缀而需要进入联合结构。

## 键宽度与覆盖的取舍

更窄的键通常能让页容纳更多项，降低索引总体空间和缓存压力。主键进入二级索引，因此主键长度的影响会扩散到多个结构。长字符串可评估前缀索引，但必须保留完整值核对和排序覆盖限制。

覆盖能减少回表，却不能无限增加索引列。把大文本和低使用率返回字段都塞进联合索引，可能让少量读收益转化成每次写入的持续维护成本。应比较读取频率、写入频率、记录宽度和缓存效果。

## 重复与冗余

完全重复定义通常没有必要。`(a,b)` 已存在时，单列 `(a)` 可能被复用前缀取代，但仍要检查唯一约束语义、索引体积、实际访问与依赖；不能只按列集合删除。

`(a,b)` 与 `(b,a)` 具有不同前导顺序，不能直接认为重复。普通索引与同列唯一索引也有不同约束含义，删除后的影响不仅是查询性能。

## 用实际证据确认

检查计划中使用的键、估计扫描量和排序方式，必要时结合实际执行信息。比较多个代表性参数与负载，既关注查询收益，也关注新增索引带来的写入、构建和存储成本。

索引设计结果会随着数据分布和访问模式变化，需要维护。全表扫描不总是问题，强制索引不总是解决方案；目标是以可接受代价完成正确的查询结果。
