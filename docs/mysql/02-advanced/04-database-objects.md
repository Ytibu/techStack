# 4. 视图、存储过程与触发器

## 4.1 视图

普通视图保存查询定义，使用时呈现相应结果，不等于事先缓存一份结果数据。它可以封装常用查询、提供稳定接口或在配合权限设计时限制可见列与记录范围；底层表改变后，视图查询也会按当前规则处理。

视图不自动让复杂查询更快。优化器如何展开或处理视图，以及是否需要临时结果，取决于定义和查询；重复关联、过滤和聚合的真实成本仍需分析。

部分视图可以更新，但含聚合、分组、DISTINCT、UNION 等结构的视图常不满足更新条件。不能把“能从视图 SELECT”推导成任意 INSERT、UPDATE、DELETE 都合法。

WITH CHECK OPTION 用于对通过可更新视图发生的插入、更新检查其是否仍满足视图条件。CASCADED 与 LOCAL 决定对相关视图条件的检查范围。它不是对所有访问基表的路径施加同一约束，也不应描述成对 DELETE 进行同样的行条件检查。[视图检查选项](https://dev.mysql.com/doc/refman/8.0/en/view-check-option.html)。

## 4.2 存储过程

存储过程在数据库中封装一组逻辑，通过 CALL 等方式调用，可以包含输入输出参数、条件、循环和 SQL。它减少某些多次往返的机会，也将一部分逻辑维护责任放到数据库端。

封装不意味着过程整体天然是一个原子事务。过程中的事务控制、调用上下文、语句行为和所用引擎都需要明确。应用如果不知道过程内部修改了哪些表、怎样处理异常，就难以正确判断回滚和重复调用的结果。

复杂业务逻辑集中在过程内，会影响版本管理、测试、扩展与跨服务协调。是否采用应依据数据处理职责和团队维护方式，而不是笼统认为“数据库执行逻辑一定更快”或“所有逻辑都必须放 Java”。

## 4.3 存储函数

存储函数是可在表达式中调用、返回值的数据库程序对象，与存储过程是不同调用形式，不能简单等同为给过程补一个返回值。函数可以封装计算，但还受到调用、事务与数据访问等限制。

确定性声明表达相同输入是否应产生相同输出，可能关联日志及执行限制。声明 DETERMINISTIC 不会自动检测并修复一个实际不确定的函数，也不能替代开发者对时间、随机值和外部状态的理解。

## 4.4 触发器

触发器与表的 INSERT、UPDATE、DELETE 事件关联，在 BEFORE 或 AFTER 阶段自动执行。MySQL 触发器按行触发，OLD、NEW 用于引用变更前后相应记录；批量修改因此可能触发多次附加处理。

触发器能统一执行某些校验或附加记录，但也让写入存在调用者不显式看到的副作用，扩大锁竞争和排查范围。排查“只执行一条 SQL 却修改其他数据”时，不能只查看 Java 调用链。

对事务表，触发器在触发语句的事务上下文中工作，不是默认独立提交的事务；不能靠触发器把任意外部操作自动变为与数据库同步的可靠副作用。唯一性、非空或引用完整性等明确规则，通常应先评估现有约束是否已经足够。

本章保留对象含义、调用方式与边界，不展开变量、游标、循环及条件处理器的逐项语法训练。
