# 3. 分库分表

## 3.1 拆分目的与策略

分库分表将数据按规则分散到不同表或实例，缓解容量、访问规模和维护成本等问题。是否需要拆分，应先确认真实瓶颈，并评估索引、查询、冷热分离和归档等方案，没有脱离记录宽度、索引和负载的固定行数门槛。

| 方式 | 划分依据 | 主要影响 |
| --- | --- | --- |
| 垂直分库 | 业务职责或表集合 | 分离业务边界，可能产生跨库关联与事务 |
| 垂直分表 | 同一对象的字段 | 分离大字段或低频字段，读取时可能需要重新关联 |
| 水平分库 | 相同结构中的不同行 | 分摊实例容量与负载，需要路由与跨库协调 |
| 水平分表 | 相同结构中的不同行 | 降低单表规模；若仍同实例，不自动增加主机资源 |

垂直分表要保持记录关联和生命周期规则。水平拆分则需要明确哪些数据去哪个分片，以及查询缺少分片条件时如何处理。单个热点对象仍可能集中在一个分片，不能认为数据总量均匀就没有访问热点。

## 3.2 MyCat 与实现位置

资料通过 MyCat 演示分片。这里保留访问代理的概念：应用连接逻辑数据库，代理解析请求、路由到物理节点，并处理相应结果。另一类实现将路由能力放在应用侧的数据访问层。

两类方式有不同的接入、维护与资源位置，但都不能自动消除跨节点的语义限制。代理能接受一条 SQL，不代表其全局排序、JOIN、事务和错误恢复拥有与单库完全相同的能力。

逻辑表是应用看到的抽象对象，物理表是实际保存记录的对象，数据节点是相应的存储位置。开发者需要理解映射，才能知道哪些条件能定向访问、哪些查询会广播到多个节点。

## 3.3–3.4 逻辑配置需要表达的内容

原资料的入门与配置章节用来建立逻辑库、表与节点之间的对应。知识库只保留规则含义：哪些表拆分、哪些表需要复制为全局数据、使用什么分片键、各分片落在哪里，以及访问失败如何处理。

全局小表可方便各分片本地关联，却产生多份数据一致维护的要求。它不意味着任意大表都应该复制到每个节点，也不意味着应用无需关心更新传播。

## 3.5 分片与规则

分片键应尽量被高频查询携带，值分布和访问负载应相对均衡，并避免频繁变化。按 user_id 路由有利于用户维度查询，但按另一业务号检索时可能需要映射或携带路由信息；单个超大用户也可能形成热点。

| 原资料涉及的规则 | 适用思路与限制 |
| --- | --- |
| 数值范围 | 便于范围路由与归档，但数据增长可能集中到末端分片 |
| 取模与固定哈希分片 | 通常有利于分布，节点数变化可能迁移大量数据 |
| 一致性哈希 | 减少某些扩容时的重新映射范围，不自动解决业务热点或迁移一致性 |
| 枚举与应用指定规则 | 映射直接、可表达业务分区，但需维护规则及未命中情况 |
| 字符串哈希或截取解析 | 依赖键格式与分布，编码规则变化可能影响路由 |
| 按天或自然月 | 便于时间范围管理，当前周期可能成为写入热点 |

取模、哈希、范围等规则之间没有脱离负载的统一最优解。还需考虑历史访问、容量增长、热点、时间范围、扩容和数据保留策略，而不是只看当前分片行数是否一致。

## 3.6 管理与开发边界

分片后，全局排序分页往往需要多个节点取得候选再归并，深分页成本可能放大；跨分片 JOIN、聚合和事务也需要相应协调或改写。带分片键的定向查询通常更容易控制成本。

本地唯一索引只约束所在分片，生成全局唯一 id 也不自动满足“同一用户只有一条有效订阅”等业务唯一规则。规则是否落在同一分片，或是否需要额外协调，必须明确。

扩容需要考虑数据迁移、路由切换、重复与遗漏检查，以及迁移期间读写一致性。中间件管理命令和监控平台不在本文展开，但这些正确性要求不会因代理封装而消失。
