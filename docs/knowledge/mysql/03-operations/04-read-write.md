# 4. 读写分离

## 4.1 读写分离的职责

读写分离将写入发往可写节点，将部分读取分担到其他节点。它依赖相应数据传播机制，但属于请求路由策略；复制负责变化怎样传播，路由负责一次查询去哪里执行。

适合分担的通常是允许一定延迟的读取。增加从库不会直接消除主库的写热点，也不能让所有读取天然具备主库当前结果。

## 4.2–4.3 一主一从与请求路由

一主一从由主库承担主要写入，从库承担读取或其他适合负载。应用、驱动层或代理需要识别请求语义，再决定访问节点。

不能只按字符串是否以 SELECT 开头判断可以发从库。SELECT FOR UPDATE 等锁定读属于特定事务流程，同一事务的后续读写也可能需要绑定同一主库连接；读副本上的锁无法保护主库中的业务修改。

路由通常要在获取连接前确定。事务已经绑定连接后，再改变线程中的路由标志，不代表连接会自动切换；在事务中途随意跨节点还可能破坏一致性预期。

### 写后读

主库提交后立即查从库，可能因复制尚未应用而查不到新记录或读到旧状态。处理方式应依据一致性要求：

| 方式 | 能力与代价 |
| --- | --- |
| 关键写后读走主库 | 语义直接，增加主库读取负载；仍应注意事务旧快照与缓存 |
| 同一事务内绑定主库连接 | 保持该事务内访问资源一致，不覆盖事务之外所有请求 |
| 等待从库应用到明确进度 | 需要位置或 GTID 等机制、等待上限与超时回退 |
| 接受最终可见 | 适合允许延迟的列表或展示，要明确用户可见行为 |

固定“若干秒内读主库”是经验窗口，不是严格证明之后所有从库都已追上；延迟异常时需要相应回退。半同步的接收确认也不等于从库已经可查询到结果。

## 4.4–4.5 双主双从与切换边界

原资料进一步展示双主双从和读写路由配置。对开发者，更重要的是当前谁可写、哪些节点提供读，以及切换期间请求可能经历什么结果。

两个节点都具备主角色能力，不代表应用可以把同一业务的冲突写入随意分发到两边。需要明确写入权威、冲突处理和旧主隔离，避免出现两个节点同时接受不兼容修改的情况。

切换会影响既有连接、重试、事务和结果确认。写请求超时或连接断开不能直接证明没有提交，重复执行需要稳定业务号与结果查询；不能换一个新请求身份重新执行扣款等不可重复副作用。

## 一致性与可用性的取舍

事务隔离控制一个数据库事务如何观察并发变化，复制进度控制不同节点拥有哪些变化，缓存又引入独立的有效期与失效规则。这三者需要分别分析，不能仅靠提高隔离级别解决落后副本或陈旧缓存。

设计读写分离时，应为接口说明允许读到多旧的数据、关键状态从哪里裁决、延迟与故障时怎样降级。单纯增加从库数量不是完整的一致性方案。
