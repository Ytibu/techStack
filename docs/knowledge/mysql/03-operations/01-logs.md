# 1. 日志

## 1.1 错误日志

错误日志记录实例启动、停止及运行中的重要诊断信息，是数据库异常时的基础线索。它不等于应用错误日志，也不完整记录每个请求的业务经过；定位一次请求还需要结合应用链路、时间与数据库观测。

路径、格式和收集方式取决于环境，不能将课程中的 Linux 路径当成所有部署的固定位置。开发者需要理解“应该从哪类证据判断问题”，无需背诵文件管理命令。

## 1.2 二进制日志

binlog 在服务器层记录相应数据与结构变更事件，主要用于复制、恢复和变更订阅。普通不改变数据或结构的 SELECT 通常不被记录；它不是保存所有请求原始文本的完整审计流。

MySQL 8.0 支持 STATEMENT、ROW、MIXED 等格式。STATEMENT 以语句事件为主，重放时需要考虑语句的不确定性；ROW 记录行变更，更明确表达结果，但大批量修改可能产生较大日志；MIXED 按条件切换。具体支持与弃用状态应以目标版本为准。

ROW 事件中的前后字段镜像还受配置影响，变更订阅程序不能假定任意事件都拥有业务需要的全部字段。消费事件也需要考虑重复、顺序、位置推进与失败恢复。

### binlog 与 redo、undo

| 信息 | 主要职责 |
| --- | --- |
| redo | InnoDB 内部重做恢复，与页修改和检查点等机制关联 |
| undo | 撤销修改、重建历史版本 |
| binlog | 服务器层变更传播与重放，供复制、恢复等使用 |

开启 binlog 的常见 InnoDB 提交路径需要协调引擎与日志。可用 prepare、记录 binlog、引擎 commit 的框架理解，再根据事务标识处理崩溃恢复。真实实现还有组提交等阶段，不应背成所有版本每笔事务固定独立刷三次盘的顺序。

这种内部协调解决引擎状态与复制日志的一致问题，不会自动把外部 MQ 或支付系统加入同一原子提交。[binlog 与提交协调](https://dev.mysql.com/doc/refman/8.0/en/binary-log.html)。

### 持久化与恢复范围

常见较强持久化配置是 `innodb_flush_log_at_trx_commit = 1` 配合 `sync_binlog = 1`，分别涉及 redo 与 binlog 的同步策略，但保证仍取决于操作系统、存储是否正确兑现同步。主库成功不自动等于从库已经拥有并应用同一事务。

时间点恢复通常需要有效数据基线与相应完整变更日志。redo 会复用空间，不是长期业务归档；只有一段 binlog、缺少起始数据，也不能自动恢复全部库。复制还可能传播误删，所以从库不等同于独立备份。

## 1.3 查询日志

通用查询日志可以提供连接与语句活动记录，但记录开销、体积和潜在敏感内容都需要考虑。它与只记录相应变更的 binlog 职责不同，也不能替代业务层审计中“谁基于何种授权做了什么”的完整语义。

## 1.4 慢查询日志

慢查询日志提供耗时语句线索，记录受到耗时阈值、最小检查行数及相关选项影响。没有日志不证明接口足够快，出现日志也不说明原因一定是缺索引。

开发分析应关注实际参数、调用次数、扫描和返回行数、计划以及等待信息。连接池等待、重复 N+1 调用、Java 对象映射等接口成本未必包含在单条数据库慢日志中。
