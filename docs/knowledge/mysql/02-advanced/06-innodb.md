# 6. InnoDB 引擎

## 6.1 逻辑存储结构

InnoDB 以表空间组织存储，内部进一步管理段、区、页与记录。开发者理解这些层次，主要是为了说明记录与索引的访问单位、键宽度、页面缓存和结构维护成本，不需要背诵每种文件的全部布局。

页是管理数据的重要单位，默认页大小常见为 16KB。聚簇索引叶页保存完整记录，二级索引叶页保存索引键与主键。记录更宽、主键更长或页填充率不同，会改变页能容纳的项数、缓存覆盖量与树结构。

表空间文件大小与当前有效记录数量不一一对应。删除可以释放页面内或引擎内部可复用空间，却未必立即缩小物理文件；索引与数据的维护也不只由业务列占用决定。

## 6.2 架构

### 内存结构

| 结构 | 主要职责 |
| --- | --- |
| Buffer Pool | 缓存需要访问的数据页、索引页等，降低重复磁盘访问 |
| Change Buffer | 在适用条件下缓冲不在内存中的非唯一二级索引页变更，之后合并 |
| Adaptive Hash Index | 根据访问情况维护的内部哈希优化，不是任意列上的通用用户哈希索引 |
| Log Buffer | 主要缓冲待写出的 redo 日志信息，与缓存数据页不同 |

Buffer Pool 中可区分空闲页、干净页和脏页。脏页表示内存内容与相应磁盘页不同，后续需要刷新，不表示数据错误。读写通常围绕内存页进行，缺页时需要读取，刷新时再写回。

Change Buffer 不适用于所有索引，例如唯一性检查会带来不同要求；它只改变部分维护时机，不消除索引更新。自适应哈希也有适用范围与开销，不应推导出开启就一定更快。

原资料将 undo 也笼统归入 Log Buffer，本文区分：undo 是回滚与版本重建的信息，具有自己的页和表空间组织；不能把它理解成全部保存在 redo Log Buffer 中。[InnoDB 内存结构](https://dev.mysql.com/doc/refman/8.0/en/innodb-in-memory-structures.html)。

### 磁盘结构与后台工作

系统表空间、每表独立表空间、通用表空间、undo 表空间与临时表空间承担不同存储职责。独立表空间通常包含一张表的数据与索引，但具体布局、默认值和日志文件数量随配置与版本变化，不应固定背成“每张表永远一个文件、redo 永远两个文件”。

后台工作包括异步 I/O、脏页清理、合并与历史版本清理等。Purge 在确认旧版本不再需要后清理相应历史；Page Cleaner 等负责脏页刷新。后台机制将部分工作从语句路径中分摊出去，但不能保证持续高负载下没有 I/O 压力。

Doublewrite 主要帮助处理页面写入不完整的问题，redo 则用于重做相应修改，两者职责不同。这里只保留恢复关系，不展开文件管理、线程数量调参或底层二进制解析。

## 6.3 事务原理

### redo 与 WAL

修改首先作用于相应内存页，同时产生 redo 信息。数据页可以稍后刷新，但在相关脏页落盘前，必须按 WAL 协议满足相应日志持久化要求。崩溃恢复据此重做必要修改，无需要求每次提交都同步写完所有数据页。

日志追加和成批刷页通常比逐个随机数据页同步写入更有利于吞吐。提交时日志达到什么保证，取决于持久化策略；“内存已经改了”“日志写到系统缓存”“日志同步到持久存储”不能视为同一阶段。

redo 空间可以在检查点推进、相应恢复需求得到满足后复用，不是长期保存全部历史的业务归档。`innodb_flush_log_at_trx_commit` 等配置影响保证与代价，降低同步频率会改变故障丢失窗口；“通常按秒刷新”不是严格最多只丢一秒的时钟承诺。[redo 日志](https://dev.mysql.com/doc/refman/8.0/en/innodb-redo-log.html)。

### undo 与回滚

undo 保存撤销修改或重建旧状态所需的信息。可以用“反向恢复”帮助理解，但它不是简单保存一条原 SQL 的反向 SQL 文本。回滚依赖这些引擎内部信息撤销事务修改。

更新和删除产生的历史信息还可能被其他事务的一致性读使用，因此提交后不一定立即删除。插入的回滚信息与更新版本历史在生命周期上也不完全相同。清理必须考虑仍然存在的读视图。

原子性、持久性、隔离性共同为一致状态提供基础，但业务一致性还依赖约束与正确逻辑。不能仅因有 redo、undo 就认为任意业务操作都满足全部不变量。

## 6.4 MVCC

### 当前读与快照读

普通 SELECT 在 RC/RR 下通常是一致性快照读，按可见性规则读取版本，可能得到历史值；SELECT FOR UPDATE、FOR SHARE 等是锁定读，修改操作也按当前记录和锁定规则处理，而不是在旧快照上直接覆盖历史。

| 访问方式 | 关键特征 |
| --- | --- |
| 普通一致性读 | 根据读视图找可见版本，通常不申请读取行的记录锁 |
| 锁定读 | 读取并获取相应锁，可能等待冲突事务，不受先前旧快照同样限制 |
| UPDATE / DELETE 等 | 对当前候选记录进行判定与修改，锁和隔离规则共同起作用 |

当前读不等于读取别人未提交的数据。遇到冲突锁仍可能等待；普通快照读不申请记录锁，也不等于没有 MDL 或任何等待。

### 记录版本信息

InnoDB 聚簇记录具有最近修改事务的信息和回滚指针等隐藏字段。DB_TRX_ID 关联最近修改事务，DB_ROLL_PTR 关联撤销信息以便重建历史。DB_ROW_ID 只在需要隐藏聚簇键时使用，不是所有表都额外拥有一个可用的隐藏主键。

没有显式主键时，还要先检查是否有合适的全非空唯一索引；不能简化为“无主键就一定使用 DB_ROW_ID”。修改事务 ID 表达相应事务身份，也不能直接当成业务提交时间。

多次修改形成可重建历史的版本链。读取先判断当前版本，若不可见，再依据 undo 寻找更早版本。引擎不需要为每个事务复制整张表。

### ReadView 与可见性

ReadView 描述一致性读判断版本可见性的依据，包含创建者及当时活跃修改事务的相关信息。核心含义是：自己的修改可见；视图建立前已提交的修改通常可见；建立时仍活跃的其他事务版本不可见；视图建立之后才分配的相应修改事务版本也不可见。

可用下界、上界和活跃集合理解判断顺序：

1. 当前版本来自自己，或其事务 ID 小于活跃下界，可以访问。
2. 事务 ID 大于等于视图记录的下一待分配 ID 上界，不可访问。
3. 位于中间区间时，检查是否仍在当时活跃事务集合中；不在其中才可见。

原资料对上界的简化表格存在等号边界问题。真实判断以相应实现为准，不可把“严格大于上界”作为通用规则。[ReadView 实现](https://github.com/mysql/mysql-server/blob/mysql-8.0.26/storage/innobase/include/read0types.h)。

### RC 与 RR 的视图时机

RC 每次一致性读建立新的视图，RR 通常在首次一致性读建立后于同一事务复用。普通 BEGIN 不代表已经立即建立快照；适用级别下 WITH CONSISTENT SNAPSHOT 可以显式请求立即建立一致性快照。

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| T1 | 开启事务，首次普通读得到状态 CREATED | |
| T2 | | 更新状态为 PAID 并提交 |
| T3 | 再次普通读 | |

在这个简单过程中，RC 的第二次读可以看到 PAID，RR 通常仍看到 CREATED。若 A 改为锁定读，则按相应当前访问规则处理；A 自己的修改也可以被后续读取看到，所以 RR 不是永远展示一份与自身写入无关的冻结表。

### 幻读与两种机制

RR 的同一快照重复范围读不会直接看到别人后来提交的新行；范围锁定访问则依赖相关记录、间隙或临键锁约束插入。MVCC 和锁分别提供相应能力，不能只用其中一个术语解释全部隔离行为。

混合快照读、锁定读和修改时，可能观察到旧视图之外的当前数据或自己的新版本。业务需要唯一性时仍应使用正确约束，需要保护判断范围时仍应设计相应访问，不能把默认 RR 当成任意“先查不存在再插入”都安全的保证。[一致性读的边界](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。

长事务可能长时间保留读视图，阻碍历史清理；还可能占用连接和锁，扩大回滚成本。MVCC 减少部分读写阻塞，但要支付历史空间、可见性判断和回收代价。
