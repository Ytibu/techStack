# 2.1–2.2 索引概述与结构

## 索引的作用与代价

索引维护额外的访问结构，使数据库有机会缩小查找范围、按已有顺序读取，或直接取得需要的列。没有合适索引时，引擎可能需要检查大量记录；有索引时，也仍要判断它能减少多少工作。

索引占用磁盘与缓存空间。插入、删除以及索引键修改，都可能触发结构维护；索引更多不等于所有查询都会更快。读取较少数据的查询可能受益很大，命中大部分记录且需要频繁回表的查询则未必。

“索引失效”容易混合几类不同现象：无法按键定位、只能扫描整个索引、优化器认为全表扫描更便宜、用了索引但仍扫描过多。分析时应具体说明访问方式。

## 按页访问与多路树

InnoDB 按页管理数据与索引，默认页大小常见为 16KB，但并不是所有实例都固定如此。访问一页可以取得多个键或多条记录，因此树的分支能力与页内可容纳内容直接影响访问成本。

普通二叉搜索树每个节点分支较少，记录很多时可能形成较深的路径；平衡约束能防止极端退化，但不能改变分支较少的特点。B 树、B+ 树采用多路结构，使较低高度能够组织大量键，更符合页式访问。

不能把树高直接等同于每次查询实际磁盘读取次数。部分上层页和叶页可能已在内存中，记录大小、键宽度和页填充率也会改变树高；“某个固定数据量必然几层”不是稳定规律。

## B 树与 B+ 树

B 树的非叶节点也可以存放数据；B+ 树将完整记录或相应数据项集中于叶节点，内部节点主要用于导航。对相同页大小，内部节点通常可以容纳较多导航项，提高分支能力。

B+ 树叶节点按键值连接，定位到范围起点后可以沿叶层顺序访问，适合范围条件和有序读取。InnoDB 使用这种组织方式，但聚簇索引与二级索引叶节点的内容不同，需要在分类中进一步区分。

有序结构不代表任意列都整体有序。多列联合索引按列顺序逐级比较，后续列通常只有在相同前导值的分组内有序，最左前缀和范围访问都源于这一点。

## 哈希结构

哈希结构将键映射到桶，适合等值查找，但没有天然保留键值大小顺序，因此不能像有序树那样直接完成一般范围遍历和排序。哈希冲突、缓存与实现细节也影响实际成本，不能断言哈希每次只需一次 I/O。

InnoDB 的自适应哈希是引擎根据访问情况维护的内部优化，不是开发者为普通业务列随意声明、从而替代所有 B+ 树索引的通用功能。全文、空间等索引也有不同用途，不应套用本章的全部普通 B+ 树规则。
