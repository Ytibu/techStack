# 2.5 SQL 性能分析

## 执行频率与主要开销

性能问题既取决于单次耗时，也取决于调用频率。一次耗时不高、却在循环里调用上千次的 SQL，可能比偶发的复杂查询更值得处理。分析应将调用次数、参数、扫描和返回数量与业务请求对应起来。

接口总耗时还可能包含连接池等待、网络与结果映射，数据库执行耗时又可能包含锁等待。先区分阶段，再判断是否应该改 SQL 或索引；不能看到接口慢就认定数据库全表扫描。

## 慢查询与阶段分析

慢查询记录提供耗时 SQL 的线索，但其出现受阈值和相关日志选项影响，不能把“没有慢日志”当成所有查询都符合接口目标。常见线索包括查询耗时、锁时间、扫描行数与返回行数，具体字段以采集方式为准。

原资料中的 SHOW PROFILE 属于已弃用的分析路径，了解其阶段分析思想即可，不作为新增方案的主线。实际可结合 Performance Schema、应用链路和执行计划观察，以免把旧版本工具演示当成跨版本通用方式。

## EXPLAIN 的主要信息

EXPLAIN 描述优化器计划如何访问数据。对多表查询，既要看单表访问，也要看连接次序与循环放大，不能只找一个非空 key 字段。

| 字段 | 含义与判断重点 |
| --- | --- |
| table | 当前访问的对象或执行步骤 |
| type | const、eq_ref、ref、range、index、ALL 等访问方式；index 仍可能是全索引扫描 |
| possible_keys / key | 候选与实际选择的索引，不保证候选都会使用 |
| key_len | 使用键前缀的最大长度线索，还受类型、字符集和可空性影响 |
| rows / filtered | 扫描数量与筛选比例的估计，不能当成运行实测 |
| Extra | 覆盖、条件下推、额外排序、临时表等补充信息 |

const 或 ref 往往具有较强定位能力，但访问方式没有脱离数据量和返回需求的绝对优劣排名。小表全扫可能足够便宜，大量重复循环的 ref 访问也可能昂贵。

`Using index` 通常表示覆盖访问；`Using index condition` 表示 ICP；`Using filesort` 表示额外排序；`Using temporary` 表示内部临时表。这些信息不能互相替代，也不直接说明所有操作是否落盘。[EXPLAIN 输出](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)。

## 估计与实际执行

统计信息、参数分布和相关性会影响估计。相同 SQL 换一个条件值，可能对应完全不同的匹配比例；当估计与实际差距较大时，需要继续检查数据分布和路径，而不是立即强制某个索引。

MySQL 8.0.18 起支持 EXPLAIN ANALYZE，它会真正执行支持的语句并返回实际执行信息，可帮助观察行数、循环和耗时。它不是纯静态命令，使用前应评估负载和语句代价，不能随意在高成本查询上执行。[EXPLAIN ANALYZE](https://dev.mysql.com/doc/refman/8.0/en/explain.html)。

验证改动时，应比较相同业务语义和有代表性参数下的结果、延迟、扫描量与资源成本。单次缓存命中或一次极端参数，不能证明优化在全部负载下都成立。
