# 1. 存储引擎

## 1.1 MySQL 体系结构

连接层处理通信、认证和连接上下文；服务层负责 SQL 解析、语义检查、优化和执行协调；存储引擎提供表数据和索引的访问实现。数据与日志最终通过相应文件和持久化机制落到存储介质。

一条查询经过解析后，优化器在合法的执行方式中选择访问路径，例如使用哪个索引、如何连接多个表。执行器按计划调用引擎接口取得或修改记录。SQL 写法只描述结果，物理访问次序可以不同。

原资料将旧查询缓存纳入服务层描述，但 MySQL 8.0 已移除该功能。InnoDB Buffer Pool 缓存数据页与索引页，属于另一种缓存，不能据此说 MySQL 8.0 完全没有缓存。[MySQL 8.0 的功能变化](https://dev.mysql.com/doc/refman/8.0/en/mysql-nutshell.html)。

## 1.2 存储引擎的职责

存储引擎决定记录如何组织、索引如何访问，以及支持什么事务与并发能力。引擎通常由表选择，不是一个数据库里的所有表必然采用同一种引擎。

服务层的 SQL 功能与引擎能力需要配合。一个业务事务如果混用了非事务表，就不能把全部修改都视为拥有相同的回滚保证；同理，其他引擎的锁行为不能直接套用 InnoDB 的行锁解释。

## 1.3 常见引擎特点

| 引擎 | 主要特点 | 理解边界 |
| --- | --- | --- |
| InnoDB | 支持事务、行级并发控制、外键和崩溃恢复，使用聚簇索引组织记录 | 同一热点记录仍会竞争，并不因行级锁而自动无冲突 |
| MyISAM | 不提供 InnoDB 式事务能力，主要使用表级锁，数据与索引文件分开 | 不能以“读取多”作为忽略事务和恢复需求的理由 |
| MEMORY | 主要将表记录存于内存，可提供哈希等索引 | 数据不能作为进程重启后仍可靠保留的业务事实来源 |

InnoDB 二级索引记录主键，聚簇索引保存完整行；MyISAM 的索引与数据组织不同。索引是否需要再次访问数据、主键长度产生什么影响，都必须在对应引擎语境下分析。

MEMORY 表不等于 Redis，也不等于 MySQL 所有内部临时表都使用的固定引擎。缓存数据、临时计算和可靠业务记录具有不同生命周期要求，应分别理解。

## 1.4 引擎选择

选择存储引擎要先看事务原子性、并发读写、恢复、约束与实际负载。Java 业务中的订单、账户和库存通常需要 InnoDB 的这组基础能力，性能优化也通常在满足这些要求的前提下进行。

没有一种引擎能仅凭名称保证某类查询一定更快。数据量、索引、记录宽度和访问方式都会影响成本。将表改成不支持事务的引擎换取某次查询耗时下降，可能改变整个业务的正确性前提。
