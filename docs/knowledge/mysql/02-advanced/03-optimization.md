# 3. SQL 优化

## 3.1 插入数据

多行插入或合理批量可以减少网络往返与提交开销。批量并非越大越好：事务越大，持锁时间、日志量、失败回滚和重试成本通常也越高，还可能影响复制进度。

按主键相对有序写入通常更有利于局部页面访问。随机键或多个二级索引仍会产生分散维护，不能仅靠批量消除。批次大小应根据记录宽度、事务时间、失败恢复和并发承载决定，不存在对所有系统通用的固定条数。

## 3.2 主键优化

InnoDB 聚簇索引按主键组织记录，插入位置由键值决定。相对有序的键可减少某些分散插入与页分裂成本，短主键还能减轻二级索引空间；但连续写入也可能竞争热点位置，分布式业务还需考虑全局身份生成。

页分裂是为了容纳新记录调整页面结构，删除后也不代表文件立即按同等大小缩小。表空间、页内空闲和物理文件尺寸是不同层次，不能用 DELETE 的影响行数直接推算磁盘释放量。

修改主键可能影响聚簇组织及其他索引引用，应尽量保持稳定。业务唯一编号可以另设唯一键，避免业务编码规则变更牵动底层记录身份。

## 3.3 ORDER BY 优化

索引的列顺序与排序要求匹配时，可以沿已有顺序取得结果。对 `(a,b,c)`，固定 a 后按 b、c 排序具有相应条件；只按 c 排序而 b 不固定，通常不能直接利用同样顺序。

同向升降序常可通过顺向或反向扫描完成，混合方向需匹配索引方向组合。是否实际选择该路径还与过滤和回表成本有关。具备索引顺序不代表一定比其他路径更便宜。

filesort 表示额外排序，不等于必然磁盘排序。优化时先减少待排序行和不必要的大字段，再判断是否值得新增索引，不能为消除一个 Extra 标签付出远大于收益的成本。

## 3.4 GROUP BY 优化

分组成本取决于输入规模、分组键顺序和聚合方式。合理过滤、利用适合的索引前缀、减少无关列都有价值；某些查询可采用特定索引分组优化，但有明确条件，不能只因存在分组列索引就保证不使用临时结构。

GROUP BY 表达分组语义，不自动承诺结果顺序。需要稳定输出时应明确 ORDER BY。连接后聚合还要先检查统计粒度，否则即使执行更快，错误累计也没有被修复。

## 3.5 LIMIT 优化

`LIMIT offset,size` 通常需要访问并跳过前 offset 个候选结果。深分页会累积无效扫描，若同时取完整行，还可能产生大量无效回表。

延迟关联先用较窄索引找到本页主键，再读取本页完整数据，可以减少取列回表，却没有消除跳过 offset 的工作。游标分页改为从上页最后的排序键继续，适合连续翻页。

```sql
SELECT id, created_at, amount
FROM orders
WHERE user_id = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

两个时间参数来自同一末尾记录，id 用于打破时间相同的情况；可评估 `(user_id,created_at,id)`。游标不擅长任意页码跳转，翻页期间的新增、删除、排序键变化也需要定义一致性范围。这是分页知识的短示意，不是经过数据集验证的固定最优 SQL。

## 3.6 COUNT 优化

COUNT(*) 与 COUNT(1) 统计行，COUNT(列) 只计非 NULL 值。不能给出脱离索引与可空性的固定性能排名，也不能说 COUNT(*) 必然读取完整行的所有列。

InnoDB 的行数必须尊重当前事务可见性，普通精确计数一般需要遍历符合条件的记录或索引项。较窄覆盖索引可减小扫描成本，但不能把大规模精确计数变成无成本操作。

如果接口只需“是否有下一页”，可以多查一条；允许延迟的统计可考虑异步或缓存。近似统计与精确计数语义不同，应明确给调用方，不能静默替换。

## 3.7 UPDATE 优化

定位条件既影响扫描，也影响加锁范围。用合适索引确定目标、限制批量规模和缩短事务，通常比仅缩减返回字段更重要。WHERE 最后匹配一行，不证明引擎只访问或锁定一行。

InnoDB 不会因为没有合适索引就按常规机制“将行锁升级成表锁”。广泛扫描可能锁住大量记录和间隙，呈现近似整表受阻的效果；实际还受隔离级别和锁释放规则影响。[加锁规则](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。
