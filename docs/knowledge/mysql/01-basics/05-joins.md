# 5. 多表查询

## 5.1 多表关系

一对多通常由“多”的一侧保存对“一”的引用；一对一还需要相应唯一性限制，否则一个普通引用列仍可能对应多条记录。多对多通常使用关联表，将一条关系保存为一行，并根据业务约束组合是否唯一。

表关系决定连接后的行数。父表一行匹配子表三行，结果通常产生三行；同时连接两个一对多集合时，还可能形成组合扩张。查询与聚合需要明确统计的是父对象、子对象还是关系行。

## 5.2 连接与笛卡尔积

笛卡尔积列出两侧记录的全部组合，行数可能是两边行数的乘积。连接条件用于限定哪些组合满足关系，漏掉连接条件不仅影响性能，也会改变结果含义。

多表查询中建议给表设置明确别名，并限定容易歧义的列。显式 JOIN ... ON 能将关联条件与其他过滤条件区分开，便于检查外连接等语义。

## 5.3 内连接

INNER JOIN 返回满足连接条件的组合。某一侧没有匹配记录时，不会为它生成保留行；匹配多次则返回多个组合，并不会默认按业务对象去重。

例如用户与订单内连接得到的是匹配的用户—订单关系行，不是“每个下过单的用户恰好一行”。如果只判断是否有订单，存在性查询通常更直接；如果需要订单明细，多行结果可能正是预期。

## 5.4 外连接

LEFT JOIN 保留左表记录，没有匹配时右表列补 NULL；RIGHT JOIN 对称地保留右表。决定保留对象后，可通过调整左右表统一使用更易阅读的 LEFT JOIN。

```sql
SELECT u.id, o.id AS order_id
FROM users u
LEFT JOIN orders o
  ON o.user_id = u.id AND o.status = 'PAID';
```

这条查询保留所有用户，只把已支付订单作为匹配项。若把支付条件改放 WHERE，未匹配行的右表状态为 NULL，会被过滤，查询就不再保留这些用户。

ON 决定匹配关系，WHERE 决定连接结果中的行是否保留。某些右表条件会使外连接在语义上可被简化为内连接，因此不能仅凭 SQL 写了 LEFT JOIN 就认定所有左表行都能返回。

统计匹配数量时应使用非空的右表标识，如 COUNT(o.id)。COUNT(*) 会把外连接产生的补空行也计为一行。

## 5.5 自连接与联合查询

自连接让同一张表以不同角色参与连接，例如员工与主管。需要使用不同别名区分角色，并根据是否保留没有上级的记录选择内连接或外连接。

UNION 与 UNION ALL 则是纵向合并结果，不是把关联列横向拼接。两侧返回列数量与类型需要可对应；UNION 对完整结果行去重，UNION ALL 保留重复。是否允许重复由结果语义决定，不能只为省去去重开销就替换。

合并后需要全局排序或分页时，应明确作用于整个合并结果。各分支局部有序，不能自动保证最终结果全局有序。

## 5.6 子查询

子查询可以作为标量值、成员集合、存在性判断或派生表参与主查询。标量子查询要求返回符合标量语义的结果，多行会产生错误；相关子查询依赖外层列，但不应据此断言一定对每个外层行低效地重复执行，优化器可能改写。

IN 表达成员关系，EXISTS 判断是否存在满足条件的行。NOT IN 尤其要注意 NULL：子查询含 NULL 时，某些看似“不属于集合”的判断会成为 UNKNOWN。排除关联对象时可使用正确关联的 NOT EXISTS，或按语义显式处理空值。

## 5.7 关联后的统计粒度

父表金额在一对多连接中会重复，直接 SUM 可能多次计算同一笔金额。处理方式应基于统计粒度，常见的是先将子表聚合到父对象粒度，再连接；或分别聚合不同集合。

`SUM(DISTINCT amount)` 只会去除相同金额值，无法识别哪些金额来自同一对象；两笔不同订单可以恰好同额。因此 DISTINCT 不是连接错误和统计粒度错误的通用修补方式。
