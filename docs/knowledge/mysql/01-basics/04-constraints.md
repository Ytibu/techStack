# 4. 约束

## 4.1 数据完整性与约束分类

约束是数据库对可接受数据的规则。在写入发生时检查规则，可以避免不同客户端各自校验、并发校验与写入之间存在空隙等问题。约束表达的是数据必须满足的条件，而不是用户界面的提示文字。

| 约束或属性 | 主要含义 |
| --- | --- |
| PRIMARY KEY | 唯一且非空的记录身份；可由多个列共同组成 |
| UNIQUE | 限制索引键重复，空值语义需单独考虑 |
| NOT NULL | 不允许该列保存 NULL |
| DEFAULT | 在符合规则的缺省写入中提供值，不替代其他校验 |
| CHECK | 检查行表达式；MySQL 8.0.16 起真正执行相应 CHECK 约束 |
| FOREIGN KEY | 检查子表与父表键之间的引用关系 |

AUTO_INCREMENT 是值生成属性，不应与“业务编号连续”混淆。分配、回滚、失败和并发都可能留下编号空洞，编号大小也不严格等于事务提交顺序。

CHECK 与 NOT NULL 也不能互相替代。CHECK 表达式为 TRUE 或因空值成为 UNKNOWN 时可以通过，因此需要禁止缺失值时仍应明确非空要求。

## 4.2 主键、唯一性与业务身份

主键用于稳定标识记录，业务唯一键用于表示业务身份，两者可分别设计。内部 id 保持稳定，外部请求号、订单号等通过单列或联合唯一键约束，有利于将记录身份和业务规则分开。

联合唯一键保护的是组合唯一，而不是每列分别唯一。`UNIQUE(tenant_id, request_id)` 允许不同租户使用相同请求号，但同租户下不能重复。若业务身份需要不可缺失，应同时考虑 NOT NULL，因为 MySQL 唯一索引允许多个包含 NULL 的键。

应用中的“先查询不存在，再插入”没有消除并发窗口。唯一约束在写入竞争时裁决冲突，应用负责根据冲突判断重复请求、业务错误或参数不一致。约束保证不能写出重复身份，幂等处理还要定义重复请求应得到什么结果。

唯一性还受字符比较规则和数据位置影响：大小写不敏感排序规则可能将不同拼写视为相等；单个分片的唯一索引不会自动约束其他分片。因此设计约束时要明确作用域。

## 4.3 外键与引用完整性

外键要求子表引用的非空键具有合法父记录。它保证的是数据库范围内的引用完整性，例如不能留下不存在父对象的引用；它不会自动实现订单必须属于当前登录用户等全部业务授权规则。

外键可以在父表删除、键值修改时采用不同动作：

| 动作 | 处理方式 |
| --- | --- |
| RESTRICT / NO ACTION | 对 InnoDB，相关引用存在时阻止不允许的操作 |
| CASCADE | 按关系传播删除或键更新 |
| SET NULL | 将子表引用改成 NULL，要求相关列允许空值 |

CASCADE 能减少维护引用的代码，但一次父记录删除可能影响大量子记录，不能把它当成没有代价的便捷选项。SET NULL 也不等于允许任意孤立业务数据，仍需判断失去父对象后记录是否有意义。

同一数据库内，外键可以提供直接的完整性保障；跨库、跨服务或分片后，常由业务流程承担部分关系维护。选择后者时，校验、删除策略、对账和异常修复都需要明确，不能只是移除约束。

逻辑删除本质是状态修改，通常不会触发与物理 DELETE 相同的外键删除动作。若“唯一手机号只限制有效用户”，必须把这条规则具体建模；简单增加 deleted 列并组成唯一键，未必能支持多次删除和重建。
