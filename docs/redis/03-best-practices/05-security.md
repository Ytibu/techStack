# 5. 命令及安全配置

## 访问边界

原文通过 Redis 被未授权访问的案例说明安全配置。核心风险是可达的 Redis 缺少合适认证与权限控制，攻击者便可能读写数据或修改危险配置。

`bind` 控制监听地址，防火墙或网络规则限制谁能连接。不能仅靠换端口保护服务；也不能把绑定所有地址解释为已经自动暴露到公网，实际还取决于网络环境。

## 身份与命令权限

应用应使用独立身份，并只授予所需 key 范围和命令。Redis 6 起可使用 ACL；共享一个高权限密码难以区分应用权限与追踪来源。

重点控制 `FLUSHALL`、`FLUSHDB`、配置管理等高影响命令。`KEYS` 的主要问题是大键空间下阻塞，应使用受控的 `SCAN` 替代日常遍历。

原文使用 `rename-command` 限制命令。知识库保留其历史背景，权限管理优先理解 ACL；具体机制与可用配置需匹配实际版本。见 [Redis 安全文档](https://redis.io/docs/latest/operate/oss_and_stack/management/security/)。

## 进程权限

以普通专用账号运行 Redis，限制配置目录和持久化目录的写入范围。即使 Redis 被误操作，较低的系统权限也能缩小影响。

原文把恶意写入 SSH 授权文件描述成“Redis 提供 SSH 免密登录”。这里予以区分：Redis 并不提供 SSH 登录；风险来自高权限进程和危险配置被滥用，进而影响宿主机文件。
