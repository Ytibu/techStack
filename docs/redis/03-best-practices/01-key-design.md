# 1. Redis 键值设计

## 1.1 清晰的 key 结构

采用 `业务名:数据名:id` 这样的稳定格式，例如 `shop:item:1001`。前缀用于区分业务、减少命名冲突，也便于定位数据；冒号只是命名约定，不会创建真实目录。

key 应简短、可读，避免加入不必要的长文本。原文“不超过 44 字节”借用了 String 值对象的 embstr 阈值，不能当成数据库 key 的编码规则或长度限制：数据库字典中的 key 主要以 SDS 保存。

## 1.2 拒绝 BigKey

BigKey 指单个值过大，或集合成员过多、整体体积过大的键。判断需同时看字节数、元素数、访问频率和命令成本，不能只设一个全业务通用阈值。

### 危害

- 大响应占用带宽和输出缓冲区，少量请求也可能产生高流量。
- 集合遍历、序列化、删除等操作耗时，阻塞其他命令。
- 某个分片独占大量数据，导致容量和流量倾斜。
- 复制、持久化与迁移成本上升。

### 发现与删除

| 方法 | 关注点 |
| --- | --- |
| `redis-cli --bigkeys` | 按类型统计较大键，结果不等于所有类型的准确内存排名 |
| `SCAN` + 类型相关长度命令 | 分批定位大值或大集合，控制扫描速率 |
| `MEMORY USAGE key` | 估算单键内存，采样和执行成本需结合数据规模考虑 |
| RDB 离线分析、流量监控 | 分析整体分布，定位高流量或异常增长 |

`SCAN` 以返回游标重新变为 0 为结束标志。某批返回空数组不代表结束，扫描期间也可能返回重复键，因此消费者要允许重复处理。

Redis 4.0 起可用 `UNLINK` 先移除键，再按对象释放成本与引用计数决定是否后台回收。旧版本或需要渐进清理时，可分批删除集合成员。异步释放也会消耗后台资源，不能无节制堆积。

## 1.3 恰当的数据类型

| 存储对象的方式 | 适合情况 | 代价 |
| --- | --- | --- |
| JSON String | 经常整对象读写 | 修改一个字段通常要重写整体 |
| 每字段一个 key | 字段需独立生命周期和访问 | key 数量与管理开销更大 |
| 一个 Hash | 经常按字段读取、更新 | 大对象仍可能成为 BigKey |

小 Hash 可能使用紧凑编码，但并非所有 Hash 都更省内存；还要看字段数量、字段长度与版本。

原文把百万字段的大 Hash 拆成多个小 Hash：`bucket = id / 100` 取整数部分，`field = id % 100`。这能缩小单键规模，但会改变批量查询和过期管理方式，分桶大小应按业务测量。

## 1.4 设计要点

命名统一，类型贴合访问方式，控制单键规模，为可过期数据设置合理 TTL。原文的 10KB、1000 个成员等数字可作检查起点，不是 Redis 的硬性限制。
