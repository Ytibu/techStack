# 3. 持久化配置优化

## 按数据用途选择

持久化提高故障后的恢复能力，也增加 fork、磁盘写入与内存开销。先判断 Redis 中的数据是否可从其他权威来源重建，以及重建需要多长时间。

- 可重建的纯缓存可以评估关闭持久化，但要能承受冷启动与回源压力。
- 会话、计数和业务状态等数据需要单独评估，不能因“用了 Redis”就一律不持久化。
- RDB、AOF 与备份应配合恢复目标选择，不能笼统地固定为“永远关闭 RDB”。

关闭持久化的主节点若自动重启为空库，可能使从节点也[同步为空库](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/#safety-of-replication-when-master-has-persistence-turned-off)，使用 Sentinel 时同样需控制重启与恢复顺序。

## 控制重写与刷盘成本

设置合适的 AOF 重写阈值，避免频繁生成新文件；观察重写时的延迟、写时复制内存与磁盘负载。给主机预留内存，避免把 `maxmemory` 设为整台机器的全部物理内存。

原文建议 `no-appendfsync-on-rewrite yes`。它在后台保存或重写期间推迟常规 AOF fsync，可能减轻磁盘竞争，也会削弱这段时间的持久性；并非关闭 AOF 记录。是否采用取决于可接受的故障丢失窗口。见 [Redis 6.2 配置注释](https://github.com/redis/redis/blob/6.2/redis.conf)。

## 控制实例与主机负载

单实例越大，全量复制、恢复和迁移通常越重。原文的 4GB、8GB 是容量规划示例，实际应结合恢复时间、写入速率和硬件确定。

避免与高 CPU 或高磁盘负载服务争抢资源。可评估在从节点生成备份来分担主节点开销，但从节点副本仍可能落后，复制也不能防止误删除传播。

优化完成后应验证“能够恢复且恢复时间可接受”，不能只检查持久化配置是否开启。
