# 2. 批处理优化

## 2.1 Pipeline 与批量命令

逐条同步发命令时，每条命令通常都要等待一次网络往返。批处理减少等待与系统调用次数，适合大量彼此独立的操作。

| 方式 | 特点 | 原子性 |
| --- | --- | --- |
| `MSET`、多字段 `HSET` 等 | 一个命令处理多个值，受具体命令能力限制 | 单条命令按其语义执行 |
| Pipeline | 连续发送多个命令，再收集响应 | 不保证整批命令不可被其他客户端插入 |
| Lua | 在服务端组织读、判断、写 | 脚本执行期间不被其他普通命令穿插，但运行错误不提供自动回滚 |

Pipeline 解决传输效率，不能替代事务或并发控制。命令 B 需要先读取命令 A 的结果再决定参数时，通常无法直接把两者静态放进同一批 Pipeline。

批次过大，会积压请求、响应和客户端内存。应按总字节数及延迟目标分批发送并及时读取响应。见 [Redis Pipeline 文档](https://redis.io/docs/latest/develop/using-commands/pipelining/)。

## 2.2 集群下的批处理

原生 `MSET`、`MGET` 等多键命令要求相关键同槽。Pipeline 中每条单键命令可以指向不同槽，但客户端必须支持按节点路由并正确汇总结果。

原文的四种策略可归纳为：

| 策略 | 取舍 |
| --- | --- |
| 逐条串行 | 实现简单，网络等待最多 |
| 按槽分组后串行 | 减少每组内等待，各组仍需依次执行 |
| 分组后并行 | 吞吐更好，但要控制并发和处理部分失败 |
| 使用相同 hash tag | 可进行同槽多键操作，但可能把数据集中到一个分片 |

某些客户端的高级批量 API 会自动拆分跨槽请求。调用看似一次，实际仍是多个节点分别执行；某组失败不会撤销其他组已经完成的写入。

选择方案时，先明确是追求吞吐还是需要整体原子性。跨槽并行能提高吞吐，不能提供跨分片事务保证。
