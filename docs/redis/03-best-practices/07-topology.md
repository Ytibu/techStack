# 7. 集群还是主从

## 先明确扩展目标

| 目标 | 通常考虑 |
| --- | --- |
| 自动故障恢复 | 主从 + Sentinel，或 Cluster 自带故障转移 |
| 分摊读取 | 增加可读取的从节点，并接受复制延迟 |
| 单机容量不足、写入分摊 | Cluster 分片 |
| 单个 key 过热 | 优化访问模型或拆分业务数据，单纯加分片未必有效 |

若单主容量与吞吐足够，主从配合哨兵通常更容易管理。Cluster 的价值是分片扩展，是否采用应根据容量、吞吐和操作语义判断。

## 集群完整性

`cluster-require-full-coverage` 决定缺少槽覆盖时，是否仍允许已覆盖部分继续服务。关闭完整覆盖要求不等于缺失槽也能访问，且还受节点故障、网络分区等条件约束。

该选择取决于业务能否接受部分数据不可用，不能把 `no` 固定当作所有系统的最佳配置。

## 带宽、数据倾斜与客户端

节点通过集群总线交换拓扑和故障信息，节点增加会带来更多协调开销。扩容时还要观察数据迁移流量，而非只看业务 QPS。

平均键数相近不代表负载均衡：一个 BigKey、热点键或过度使用相同 hash tag 都可能让单节点成为瓶颈。客户端还需支持槽路由、重定向和拓扑刷新。

## 命令、Lua 与事务

Cluster 支持同槽多键命令、Lua 和事务，但迁槽期间仍可能返回 `TRYAGAIN`，客户端需处理重试或失败。跨槽拆分执行则无法保留同一原子操作的语义。

Redis 事务把排队命令按序执行，运行时某条命令出错不会自动回滚之前的命令。不要把同槽事务进一步理解为关系型数据库的完整事务能力。见 [Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)与[事务说明](https://redis.io/docs/latest/develop/using-commands/transactions/)。
