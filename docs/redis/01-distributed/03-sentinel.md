# 3. Redis 哨兵

## 3.1 哨兵原理

Sentinel 为主从架构提供监控、故障转移和主节点发现。它不保存业务键值，也不代理每一次数据请求。

### 主观下线与客观下线

- **主观下线**：一个哨兵在规定时间内没有获得实例的有效响应，自行判断实例不可达。
- **客观下线**：达到配置的 `quorum` 数量的哨兵认可主节点下线。

客观下线由 quorum 判定，故障转移还需选出执行者并获得不少于 quorum 且超过半数的哨兵授权。见 [Sentinel 的 quorum 说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/#quorum)。

### 新主选择与切换

先排除断连过久等不适合提升的从节点，再依次比较：

1. `replica-priority`，较小值优先，0 表示不参与提升。
2. 复制偏移量，较大值通常说明数据更新。
3. 运行 ID，作为前面条件相同时的确定性排序依据。

选定后，哨兵将候选节点提升为主节点，通知其他从节点跟随它，并在旧主恢复后把旧主改为从节点。客户端随后通过哨兵发现新主并更新连接。

## 3.2 哨兵集群

哨兵自身也需要多个实例，并分散故障域。只有一个哨兵时，它本身故障或网络隔离就会影响自动恢复。

配置的核心是受监控主节点名称、地址、quorum 和下线判定时间。阈值太短容易因抖动误判，太长会增加恢复时间。

故障切换存在检测、选举、提升和客户端重连时间；哨兵提供自动恢复，不承诺全程无中断或写入零丢失。

## 3.3 RedisTemplate 接入

客户端应配置主节点的逻辑名称和多个哨兵地址，由支持 Sentinel 的连接工厂发现实际主节点，不能把旧主地址固定写死。

Spring Data Redis 的 `RedisTemplate` 负责统一操作接口，底层 Lettuce 或 Jedis 负责连接和拓扑处理。配置项前缀随 Spring Boot 版本变化，应以项目版本为准。

使用 Lettuce 时，可按业务选择读取策略：

| 策略 | 行为 |
| --- | --- |
| `MASTER` | 从主节点读取 |
| `MASTER_PREFERRED` | 主节点优先，不可用时尝试从节点 |
| `REPLICA` | 从从节点读取 |
| `REPLICA_PREFERRED` | 从节点优先，不可用时尝试主节点 |

允许读从节点意味着接受复制延迟。启用读写分离前，应明确哪些请求允许旧值、哪些请求需要路由到主节点。
