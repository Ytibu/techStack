# 4. Redis 分片集群

## 4.1 分片集群的作用

Redis Cluster 将数据分散到多个主节点，每个主节点可以带从节点。它扩展容量和总体读写吞吐，并为分片提供故障转移能力；单个热点键仍由其所在分片承担。

非分片架构的从节点复制完整数据，Cluster 的从节点仅复制对应主节点的分片；Sentinel 负责监控与切换，不保存业务数据。

## 4.2 散列插槽

Cluster 使用 16384 个插槽，键先映射到槽，再由槽确定节点：

```text
slot = CRC16(key 的有效部分) % 16384
```

一般以完整 key 计算；存在符合规则的非空 `{...}` 时，使用其中内容作为 hash tag。例如 `order:{42}:info` 与 `order:{42}:items` 会进入同一槽。

同槽适合需要一起执行多键命令的数据，但把所有键都设置为同一个 tag 会造成数据倾斜。同节点不等于同槽，Cluster 的多键操作限制通常要求同槽。

## 4.3 集群伸缩

扩容的主要过程是“加入新节点 → 分配或迁移插槽 → 迁移相应键 → 更新拓扑”。只加入一个没有槽的主节点，不会自动分担现有数据。

请求发错节点时，服务端通常返回重定向，由支持 Cluster 的客户端重试：

- `MOVED`：目标槽由另一节点负责，客户端应向返回地址重试并更新槽路由，首次请求发错节点也会收到。
- `ASK`：槽正在迁移，本次按指定方式临时访问目标节点。

原文“任意节点最终转发到正确节点”在这里改为客户端重定向，避免误以为普通 Redis 节点会代理请求。见 [Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。

## 4.4 故障转移

集群节点交换状态，满足故障判定和选举条件后，将故障主节点的合适从节点提升为新主。需要足够的主节点参与授权，网络分区时不保证所有分区都可继续写入。

在从节点执行 `CLUSTER FAILOVER` 可请求计划内切换。默认模式会协调复制进度；`FORCE` 跳过与旧主的部分协调，`TAKEOVER` 进一步绕过正常授权，风险更高，不能当成等价的日常切换方式。

## 4.5 RedisTemplate 访问分片集群

连接工厂使用 Cluster 节点列表作为发现入口，底层客户端维护槽路由，并处理拓扑变化。节点列表不是仅允许访问这些节点，集群公布的节点地址都应能被客户端访问。

普通多键命令、Lua 脚本和事务中的相关键必须同槽，但迁槽期间仍可能返回 `TRYAGAIN`，客户端需处理重试或失败。支持跨槽拆分的客户端批量 API，本质上是多次请求，不能提供跨分片原子性。
