# 2. Redis 主从

## 2.1 主从架构

主节点处理写入，从节点复制主节点数据，并可承担读请求。主从扩展读能力、增加数据副本，但不会把同一份数据拆开存储，也不直接扩展单主写能力。

复制通常是异步的。从节点可能读到旧数据，主节点故障时也可能丢失尚未复制的写入。

## 2.2 主从数据同步原理

### 全量同步

首次复制或无法补齐缺失历史时，需要全量同步：

1. 从节点发出复制请求，携带复制历史标识和偏移量等信息。
2. 主节点确认无法部分重同步，告知本次复制信息。
3. 主节点生成并传输 RDB，从节点加载它建立基线。
4. 主节点继续发送快照期间及之后的写入，从节点重放并追赶。

RDB 可以落盘后传输，也可使用无盘复制直接传输。全量同步会消耗 CPU、内存、网络与可能的磁盘 I/O。

### 增量同步

短暂断连后，若主节点仍保留缺失的复制历史，就只发送缺少的部分。关键不是“之前连过”，而是**复制历史仍可识别，且需要的偏移量仍在保留范围内**。

`replid` 标识复制历史，`offset` 表示复制流进度。主节点根据这些信息判断能否续传，不能仅以 replid 相同就断定一定能增量同步。

### repl_backlog

`repl_backlog` 是主节点内存中的有限复制积压缓冲区，可理解为环形缓冲区；它不是磁盘日志文件。新数据持续覆盖旧历史。

从节点断连太久，所需数据已经被覆盖，就只能重新全量同步。容量估算可从“复制流写入速率 × 希望覆盖的断连时长”出发，再留出波动余量。

## 2.3 主从同步优化

- 控制单实例数据规模，降低快照与重新加载成本。
- 合理设置 `repl-backlog-size`，减少短暂故障引起的全量同步。
- 评估 `repl-diskless-sync`，在磁盘较慢而网络充足时减少落盘开销。
- 避免主节点挂载过多从节点；链式复制能分担传输压力，也会增加复制链路和延迟。

## 2.4 主从的能力边界

主从负责复制，自动判断故障并提升新主通常由哨兵或 Cluster 机制完成。读写分离适合允许短暂延迟的读取；刚写完必须读到新值的请求，可选择主节点读取，但仍要考虑故障切换时的丢失风险。
