# 1. Redis 持久化

## 1.1 RDB 持久化

RDB 将某一时刻的内存数据保存为快照，重启时加载快照恢复。它保留数据状态，不逐条保存此前的修改过程。

### 执行时机

| 方式 | 含义与影响 |
| --- | --- |
| `SAVE` | 主线程同步生成快照，期间阻塞其他命令 |
| `BGSAVE` | fork 子进程写快照，主进程继续服务；fork 本身仍可能产生停顿 |
| `save 60 1000` | 距上次成功保存超过 60 秒且累计修改至少 1000 次时，尝试触发后台快照 |
| 正常关闭 | 是否生成最终快照取决于持久化配置及关闭选项，不能推导为异常退出也会保存 |

`dbfilename` 指定文件名，`dir` 指定工作目录；`rdbcompression` 影响压缩率与 CPU 开销。`save ""` 关闭按规则自动生成快照。

### fork 与写时复制

1. 主进程 fork 子进程，最初共享已有物理内存页。
2. 子进程读取快照视图，写出新的 RDB 文件。
3. 父进程修改共享页时，通过写时复制保留子进程需要的旧内容。
4. 快照成功后，以新文件替换旧文件。

写时复制按内存页工作，并非每次复制整个数据集。写入越密集，需要复制的页面可能越多，因此后台快照仍要预留内存和磁盘吞吐。

## 1.2 AOF 持久化

AOF 记录用于重建数据的写操作，恢复时重放。理解它要区分三个阶段：命令执行、写入缓冲及文件、同步到持久存储。

### 刷盘策略

开启方式为 `appendonly yes`，刷盘策略由 `appendfsync` 控制：

| 策略 | 特点 |
| --- | --- |
| `always` | 高频同步，持久性更强，写入成本更高 |
| `everysec` | 通常每秒同步一次，在性能与持久性之间折中；故障可能丢失最近约一秒写入 |
| `no` | 由操作系统安排同步，故障丢失窗口更不确定 |

数据进入系统页缓存不等于已经持久化。刷盘策略也不能替代备份和恢复验证。

### AOF 重写

多次覆盖同一键会产生冗余历史。`BGREWRITEAOF` 根据当前数据生成更紧凑的恢复内容，而非逐行编辑旧日志。例如多次修改计数器，恢复只需要建立最终值。

自动重写同时考虑增长比例 `auto-aof-rewrite-percentage` 和最小体积 `auto-aof-rewrite-min-size`，避免小文件频繁重写。

Redis 7.0 起使用多文件 AOF：基础文件、增量文件和清单共同组成恢复数据，不能只备份一个旧式 `appendonly.aof`。见 [Redis 持久化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)。

## 1.3 RDB 与 AOF 对比

| 对比项 | RDB | AOF |
| --- | --- | --- |
| 保存内容 | 时间点快照 | 重建所需写操作；基础文件也可能使用 RDB 格式 |
| 恢复特点 | 通常加载更快，便于独立备份 | 恢复成本受日志规模与重写情况影响 |
| 丢失窗口 | 最近快照之后的更新 | 受刷盘策略与故障情况影响 |
| 主要成本 | fork、快照 I/O、写时复制 | 持续追加、同步、后台重写 |

可重建缓存可以按重建成本决定是否持久化；重要状态应综合评估持久化、复制和备份。开启两种机制也不等于每次写入都绝不丢失。
