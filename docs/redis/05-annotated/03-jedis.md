# 3. Jedis 客户端

## Java 客户端的职责

Jedis 和 Lettuce 提供 Redis 命令、连接等访问能力。Spring Data Redis 在它们之上提供统一抽象；Redisson 则提供更丰富的分布式对象和同步工具。

本节按原文复习 Jedis 的连接与池化，不展开依赖安装和完整测试工程。

## 3.1 连接、操作与释放

Jedis 把 Java 方法调用转换为 Redis 命令，解析响应后返回结果。使用前配置地址、认证和超时，结束后释放连接。

传统 Jedis 连接对象不应让多个业务线程并发共享。频繁建立、认证并销毁连接也会增加延迟，因此应用通常使用连接池。

## 3.2 连接池

```java
try (Jedis jedis = jedisPool.getResource()) {
    jedis.set("shop:status", "ready");
    String status = jedis.get("shop:status");
}
```

这里的 `close()` 通常将借用资源归还连接池；连接池本身应在应用结束时关闭。使用 try-with-resources 可避免异常路径遗漏归还。

| 配置维度 | 意义 |
| --- | --- |
| 最大连接数 | 同时占用资源的上限 |
| 最大、最小空闲数 | 在复用效率与资源占用之间平衡 |
| 借用等待时间 | 池耗尽时最多等待多久 |
| 连接与读取超时 | 分别约束建连、等待服务端响应 |

连接数不是越大越好。命令执行主要串行，过多连接可能只增加排队和资源占用。池等待超时与 Redis 命令超时需要区分，前者常指应用尚未拿到连接。

原文通过连接工厂集中管理连接池，目的是统一配置和生命周期；不必为所有项目照搬静态工厂写法，在 Spring 中也可交由容器管理。
