# 5. 缓存同步

## 5.1 数据同步策略

| 策略 | 做法 | 主要边界 |
| --- | --- | --- |
| 设置有效期 | 到期后重新加载数据 | 到期前可能保留旧值 |
| 业务同步维护 | 修改数据库后同步更新或删除缓存 | 有业务侵入，仍存在并发窗口与部分失败 |
| 异步通知 | 数据变更后通过消息或日志通知缓存端 | 解耦，但存在传播延迟和消费失败 |

同步调用数据库与缓存，不会自动形成一个原子事务。原文“同步双写即强一致”的表述在这里保留为“时效性较高”，实际还要处理更新顺序、失败重试和并发回填。

原文的 MQ 方案由业务主动发送变更事件；Canal 方案从数据库日志获取变更，减少业务代码侵入。两者都需要关注事件是否丢失、重复或乱序。

## 5.2 Canal 原理

Canal 订阅并解析 MySQL 的 binlog，把数据库变更转成客户端可消费的事件：

```text
数据库提交变更 → binlog → Canal → 缓存消费者
```

它使用类似复制客户端的方式获取增量日志，并不是周期性扫描整张业务表。部署前提包括正确的 binlog 配置、账号权限和表过滤规则。

## 5.3 监听变更并同步缓存

原文监听商品相关表的插入、更新、删除事件，将变更同步到 Redis 与 JVM 缓存。可按读取成本选择“删除后回源”或“按事件更新”。

- 删除缓存天然便于重复执行；直接更新时可比较业务版本，防止旧事件覆盖新值。
- 消费失败需重试，不能只打印日志后确认成功。
- 删除事件应删除相应条目，避免用缺少完整字段的事件重新构造对象。
- 多个 JVM 的本地缓存都需要失效；只通知其中一台会留下旧值。

原案例的 OpenResty 共享字典主要依赖 TTL 更新，Canal 修改 Redis 并不会自动清除所有 OpenResty 本地条目。这层旧值可能继续存在到到期；若业务不能接受，需要另行传播失效事件或缩短缓存周期。

异步同步适合可容忍短暂延迟的数据展示。最终交易判断仍应查询权威状态，不能把缓存更新完成等同于业务一致性已经得到完整保证。
