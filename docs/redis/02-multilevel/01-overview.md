# 1. 什么是多级缓存

## 请求经过的缓存层次

常见单级方案由 Java 服务先查 Redis，未命中再查数据库。即使命中 Redis，每次请求仍然经过应用服务，并产生一次网络访问。

原文将缓存放到请求经过的多个位置：

```text
浏览器缓存（适用的资源）
  → 接入 Nginx
  → OpenResty 本地缓存
  → Redis
  → Java 服务的 JVM 缓存
  → 数据库
```

命中某层后即可返回，后面的层次不再访问。OpenResty 直接访问 Redis，让部分查询在进入 Java 服务前完成。

## 各层的职责

| 层次 | 优点 | 代价 |
| --- | --- | --- |
| 浏览器 | 可直接减少服务端请求 | 受 HTTP 缓存规则和客户端行为影响 |
| OpenResty 本地缓存 | 靠近接入层，减少后端调用 | 多台实例间不自动共享数据 |
| Redis | 多实例应用可共享，集中管理 | 需要网络访问，仍有容量与吞吐上限 |
| JVM 缓存 | 无网络调用，读取延迟低 | 占用堆内存，各进程独立 |
| 数据库 | 提供持久业务数据 | 承担最终回源，需防止突发流量压垮 |

## 适用范围

适合读取量大、热点集中、允许一定更新延迟的数据，例如商品展示信息。库存展示值可缓存，最终扣减仍应由权威存储和并发控制决定。

层数增加后，失效传播、容量管理和故障降级都会更复杂。选择层次应围绕请求瓶颈与一致性要求，并非缓存越多越好。
