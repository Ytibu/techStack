# 3.2 过期处理与内存淘汰

## 过期 key 的处理

Redis 记录带过期时间键的到期信息。到期后，正常访问应按过期键处理，但这不代表到期瞬间就已经回收所有物理内存。

- **惰性删除**：访问键时检查，到期则处理并按不存在返回。
- **定期清理**：在维护任务中主动检查一部分到期键，控制清理耗时，避免长期无人访问的过期数据一直积累。

原文介绍周期任务中的 SLOW 清理和事件循环附近的 FAST 清理。其时间预算、抽样方式和执行条件属于实现细节，重点是同时兼顾回收效率与请求延迟。

大量键在相近时间到期，会增加回收与回源压力。TTL 加入适当随机量可以分散时间，但不解决 Redis 整体不可用等其他问题。

## 内存淘汰

过期处理围绕 TTL，内存淘汰围绕内存压力。即使键没有到期，也可能因淘汰策略被删除；反之，设置了 TTL 也不保证内存达到上限时一定有足够候选键。

| 策略 | 候选范围 | 选择依据 |
| --- | --- | --- |
| `noeviction` | 不主动淘汰 | 超出 maxmemory 时按命令类别拒绝受限操作，缩短值的 SET 也可能被拒绝 |
| `volatile-ttl` | 带 TTL 的键 | 更早到期者优先 |
| `volatile-random` | 带 TTL 的键 | 随机 |
| `allkeys-random` | 全部键 | 随机 |
| `volatile-lru` | 带 TTL 的键 | 近期较少使用 |
| `allkeys-lru` | 全部键 | 近期较少使用 |
| `volatile-lfu` | 带 TTL 的键 | 访问频率较低 |
| `allkeys-lfu` | 全部键 | 访问频率较低 |

`volatile-*` 没有足够可淘汰键时，也可能无法释放所需空间。重要业务状态不能仅因 TTL 很长就认为一定不会被淘汰。

## LRU 与 LFU

LRU 关注最近是否访问，LFU 关注一定时间内是否频繁访问。Redis 使用近似算法，避免为所有键维护昂贵的精确全局顺序。

LFU 使用带概率增长和时间衰减的紧凑计数器。频繁访问使它更容易保留，历史热点冷却后计数会衰减，防止永久占据缓存。原文的概率公式有误，此处保留机制，不照搬公式。见 [Redis 淘汰策略文档](https://redis.io/docs/latest/develop/reference/eviction/)。

选择策略时要结合访问分布和数据用途：纯缓存可在全部键中淘汰，必须保留的数据应评估单独实例与容量保障，不能只靠更换算法解决。
