# 1.2 ZipList、QuickList 与 SkipList

## ZipList：连续内存中的紧凑序列

ZipList 将多个 entry 连续保存，减少普通链表每个节点的指针和分配开销。entry 包含前一节点长度、自身编码与内容，可保存字符串或整数。

它适合较小集合：内存紧凑、局部性较好。按值查找通常仍要遍历；修改可能触发重新分配和内存移动，不能简单把所有首尾插入、删除都当作无代价的 O(1)。

### 连锁更新

前一节点长度字段使用可变字节数。当一个节点变大，后继节点用于记录它长度的字段可能从 1 字节扩成 5 字节；后继自己又因此变大，继续影响下一个节点。

这种连续调整叫连锁更新。它并非每次修改必然发生，但说明紧凑存储需要付出更新成本。

## QuickList：分段紧凑存储

QuickList 将多个紧凑块通过双向链表连接。原文的 Redis 6.x 实现以 ZipList 作为块内结构，避免所有列表内容都放在一段过大的连续内存中。

- 块内紧凑，减少节点开销。
- 控制每块大小，缩小单次内存移动范围。
- 保留双端访问能力。
- 可压缩中间部分块，以 CPU 成本换取空间。

原文的 `list-max-ziplist-size` 用于控制块的容量，`list-compress-depth` 控制两端保留不压缩的深度。参数名称和块内结构需结合版本查看。

## SkipList：有序集合的跳跃索引

SkipList 在有序链表上增加多层前进指针。查找时先通过高层跳过大段元素，再逐层下降到目标位置，平均查找、插入、删除复杂度为 O(log N)。

Redis 的有序集合节点关联 member 与 score，先按 score 排序，同分时按 member 字节序排序。层内跨度可帮助计算排名，底层后退指针支持反向遍历。

## 版本边界

ZipList 是理解原资料的历史结构。Redis 7.0 起，相关紧凑编码转向 Listpack，QuickList 的紧凑块也采用 Listpack；后者不依赖前一 entry 的长度字段，避免上述连锁更新机制。

理解“紧凑结构节省空间，大规模后转换为更便于访问的结构”比背诵所有历史字节布局更有用。版本和阈值可核对[内存优化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)。
