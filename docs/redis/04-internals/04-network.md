# 2. Redis 网络模型

## 2.1 用户空间与内核空间

应用通常通过系统调用使用网络设备。以典型 socket 读取为例，可分为两个阶段：等待数据就绪，以及把数据从内核缓冲区复制到用户缓冲区。

用户态与内核态的隔离提供权限边界；调用、复制与调度都有成本。原文的 32 位地址空间划分是示例，并非所有系统固定采用同一比例。

## 2.2 五种 I/O 模型

| 模型 | 等待数据时 | 数据复制与完成通知 |
| --- | --- | --- |
| 阻塞 I/O | 读取调用阻塞 | 数据复制完成后返回 |
| 非阻塞 I/O | 未就绪时立即返回，调用者决定何时重试 | 典型同步读取仍由调用者发起并等待复制 |
| I/O 多路复用 | 通过 select / poll / epoll 等等待多个描述符就绪 | 就绪后再执行相应读写 |
| 信号驱动 I/O | 通过信号得知就绪 | 收到通知后再发起读取 |
| 异步 I/O | 提交操作后可继续其他工作 | 完成机制通知操作结果 |

非阻塞只表示不在未就绪时等待，不等于自动高效；不断忙轮询会浪费 CPU。多路复用通知的是就绪事件，也不等于所有数据已经复制到应用。

## 2.3 select、poll、epoll

| 方式 | 主要特点 |
| --- | --- |
| select | 使用描述符集合，常见实现受 FD_SETSIZE 约束，每轮需准备集合并扫描 |
| poll | 用数组描述监听对象，摆脱 select 位图的固定限制，但仍有扫描开销 |
| epoll | 内核维护关注集合，返回就绪事件，适合大量连接但只有部分活跃的场景 |

epoll 的常用接口：`epoll_create` 创建实例，`epoll_ctl` 增删改关注项，`epoll_wait` 等待并取得就绪事件。它仍受系统文件描述符、内存和事件处理能力限制，不是无限连接。

### LT 与 ET

- **LT，水平触发**：只要就绪条件仍满足，就会继续通知。
- **ET，边沿触发**：主要在状态变化时通知，通常配合非阻塞操作，持续读写到 `EAGAIN` 等状态。

例如到达 2KB 数据却只读取 1KB，LT 通常还能因剩余数据再次通知；ET 下若只等下一次通知，可能遗漏仍待处理的数据。

## 2.4 基于事件循环的处理

服务器监听连接；接入新连接后注册读写事件；就绪时读取请求、解析命令、执行，再安排响应写出。一个线程可以管理许多连接，不需要为每条连接建立一个工作线程。

同一条慢命令依然可能占住命令执行线程。I/O 多路复用解决连接等待，不能消除命令自身的计算与遍历成本。

## 2.5 Redis 是单线程吗

原资料以 Redis 6.x 解释：核心命令执行主要串行进行；后台还存在持久化子进程、异步释放等工作，Redis 6 又引入可配置的多线程网络 I/O。

因此“Redis 单线程”通常在说主要命令执行路径，不是在说整个进程只有一个线程。减少共享数据竞争和切换开销能简化实现，但性能瓶颈仍可能来自 CPU、网络、内存访问或后台资源竞争。

多线程网络 I/O 不表示普通命令开始任意并发修改数据。不同版本实现会变化，复习时应区分网络处理与命令执行。
