# 联合索引

联合索引把多个列按指定顺序组织在同一棵索引树中。理解它的关键，是掌握多列数据的排序规则，再据此判断查询能够缩小多大的查找范围，以及能否利用索引完成过滤、排序和取列。

本文以 **MySQL 8.0、InnoDB、普通 B+ 树二级索引**为讨论范围。示意中的索引定义为 `(a, b, c)`，三个列均为非空整数，按默认升序排列；表的主键为 `id`，另有不在该索引中的列 `payload`。示例只解释机制，不需要准备项目或执行建表步骤。

## 1. 定义与用途

单列索引按一个列的值组织数据，联合索引按多个列组成的键组织数据。例如 `(a, b, c)` 是一个包含三个列的索引，而分别建立 `(a)`、`(b)`、`(c)` 会得到三个不同的索引。

这两种结构提供的访问能力不同。联合索引保留多列之间确定的组合顺序，可以服务组合条件，也可能提供查询所需的排序和列值。多个单列索引即使能通过 Index Merge 等方式组合使用，也不会因此变成按 `(a, b, c)` 排序的一棵树。

“联合”描述索引包含多个列，“唯一”描述是否允许重复键，“二级”描述其与完整行数据的存储关系。这些是不同维度：联合索引可以是普通索引，也可以是唯一索引；联合主键也属于多列索引。

本篇讨论的二级索引叶节点保存索引列与主键值。读取索引没有保存的列时，通常要根据主键再访问保存完整记录的聚簇索引，这一步称为**回表**。这一点是理解后面覆盖与过滤作用的基础。[联合索引说明](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[聚簇与二级索引说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-index-types.html)。

## 2. 多列索引的排序规则

`(a, b, c)` 采用逐列比较的顺序：先比较 a；a 相同时比较 b；a、b 都相同时再比较 c。可以把它理解为多级排序。

下面列出一组已经按这个规则排列的索引键。序号仅表示观察顺序，不是表的主键。

| 序号 | a | b | c |
| --- | --- | --- | --- |
| 1 | 1 | 10 | 2 |
| 2 | 1 | 10 | 8 |
| 3 | 1 | 20 | 3 |
| 4 | 1 | 20 | 7 |
| 5 | 1 | 30 | 2 |
| 6 | 2 | 5 | 9 |
| 7 | 2 | 10 | 1 |
| 8 | 2 | 10 | 6 |
| 9 | 3 | 10 | 4 |

从这组数据可以看到：

- a 在整个索引中有序，相同 a 的记录聚在一起。
- b 在每个相同 a 的分组内有序，但跨分组可能从较大值回到较小值，例如 30 后面出现 5。
- c 在每个相同 `(a, b)` 的分组内有序，跨分组同样可能重新从较小值开始。

所以，多列索引的有序性带有前提：**前面的列固定后，后面的列才在相应范围内形成可直接利用的顺序。**

上表省略了主键。对于 InnoDB 二级索引，主键还参与索引记录的组织；即使多个记录的 `(a, b, c)` 相同，也不能把它们理解为无法区分的同一条记录。本文先聚焦显式定义的三列顺序。[InnoDB 索引扩展说明](https://dev.mysql.com/doc/refman/8.0/en/index-extensions.html)。

## 3. 最左前缀及其原因

联合索引的最左前缀，是从第一列开始连续取出的列组合。`(a, b, c)` 的最左前缀包括 `(a)`、`(a, b)`、`(a, b, c)`。

以前面的索引键为例，条件 `a = 1` 对应序号 1–5；增加 `b = 10` 后缩小为序号 1–2；再增加 `c = 8` 后只剩序号 2。条件沿着索引列顺序逐步限定，可以定位越来越小的连续区间。

如果只有 `b = 10`，符合条件的键分散在不同 a 分组中，不能沿用上述连续前缀定位方式。如果条件是 `a = 1 AND c = 8`，可以先定位 a 的分组，但由于没有限定 b，c 在这个分组内并不整体有序，不能把它当成紧接 a 的第二列来定位。

| 条件 | 按普通连续前缀访问的理解 |
| --- | --- |
| `a = 1` | 可以利用第一列定位 |
| `a = 1 AND b = 10` | 可以利用前两列共同定位 |
| `a = 1 AND b = 10 AND c = 8` | 可以利用三列共同定位 |
| `a = 1 AND c = 8` | 可先按 a 定位；c 仍需进一步判断 |
| `b = 10` | 缺少 a，不能直接按同样的前缀方式定位 |

这里讨论的是**索引定义的列顺序**。把 WHERE 写成 `b = 10 AND a = 1`，不会把索引顺序改成 `(b, a, c)`，通常也不妨碍使用 `(a, b)` 前缀。

缺少前导列也不能一概写成“索引完全失效”。优化器可能选择全索引扫描；MySQL 8.0.13 起还存在满足特定条件时的 Skip Scan（跳跃扫描），可枚举前导列值，再在各个分组内进行范围访问。这是有条件的访问策略，不是设计索引时可以默认依赖的保证。[联合索引说明](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[跳跃扫描条件](https://dev.mysql.com/doc/refman/8.0/en/range-optimization.html#range-access-skip-scan)。

## 4. 等值条件与范围条件

### 4.1 等值条件逐步固定前缀

`a = 1 AND b = 10 AND c = 8` 可以逐列固定键值。前面的列固定后，下一列的有序性就可以用于进一步缩小查找区间。

这里的“等值”不应只按 SQL 里是否出现一个等号机械分类。例如某些 IN 条件可以展开为多个等值区间，后续列仍有机会参与区间构造。因此，不能把所有 IN 条件都当成“后续列停止使用”的同一种范围条件。

### 4.2 范围条件改变了后续列的作用

考虑以下查询：

```sql
SELECT id, payload
FROM records
WHERE a = 1 AND b > 10 AND c = 7;
```

如果按 `(a, b, c)` 进行普通范围访问，可以先确定 a 为 1、b 大于 10 的范围，即上表序号 3–5。这个范围包含多个 b 值，c 会随着 b 分组变化而重新排列，因此 `c = 7` 通常不能继续像等值前缀那样，把它收窄成仅包含目标记录的连续区间。

但 c 的值仍保存在索引记录中，可以用来排除序号 3、5，保留序号 4。**后续列没有继续缩小查找区间，不等于后续列没有作用。**

`>=`、`<=` 与 `>`、`<` 的区间边界不同，但不能据此归纳出“把 > 改成 >=，后面的索引列就全部生效”。对于一般多列范围构造，遇到这类范围比较后，后续键列通常不再继续参与区间构造；实际计划还可能包含其他优化。边界条件必须服从查询含义。[多列索引的范围访问](https://dev.mysql.com/doc/refman/8.0/en/range-optimization.html#range-access-multi-part)。

## 5. 索引列参与查询的四种作用

判断联合索引的使用情况时，需要分别看定位、过滤、排序和取列。它们可能由同一个索引同时完成，也可能只完成其中一部分。

| 作用 | 解决的问题 | 主要收益 |
| --- | --- | --- |
| 定位查找区间 | 从哪里开始、扫描到哪里结束 | 减少需要扫描的索引记录 |
| 在索引中判断条件 | 哪些候选记录可以提前排除 | 在适用下推时减少无效回表 |
| 按索引顺序读取 | 结果能否直接满足要求的顺序 | 减少额外排序 |
| 从索引取得所需列 | 是否还要读取完整记录 | 覆盖查询通常可减少取列回表 |

### 5.1 索引条件下推

前面的范围查询需要返回 payload，而索引只包含 a、b、c 和主键。若先把范围内每条记录都回表，再判断 c，就可能读取无用的完整记录。

**索引条件下推（ICP）**允许存储引擎先对可下推的索引条件进行判断，通过后再读取完整记录。在这个示意中，`c = 7` 是可以在索引记录上判断的条件；若计划采用相应下推，就能先排除不符合 c 条件的候选项。

对 InnoDB，ICP 用于适用的二级索引访问，是否采用还要看访问方式、条件及优化器选择。执行计划中的 `Using index condition` 是下推的线索，不能把它简单解释成“发生了回表”。[ICP 的处理过程与限制](https://dev.mysql.com/doc/refman/8.0/en/index-condition-pushdown-optimization.html)。

### 5.2 覆盖索引

如果把返回列改为 `id, a, b, c`，条件和返回列都可以由该二级索引提供，就具备覆盖查询的条件，通常无需为了取得 payload 等其他列而回表。

覆盖是查询与所用索引之间的关系，不是额外的一种索引类型；判断时也要看 WHERE、ORDER BY 等位置需要的列，不能只看 SELECT 列表。事务可见性检查等情况仍可能涉及聚簇记录，因此不应将其扩展成任何场景都绝不访问聚簇索引的保证。

执行计划中的 `Using index` 通常表示覆盖访问，`Using index condition` 表示索引条件下推。二者表达不同作用，也都不能单独证明排序已经消除。[EXPLAIN 的 Extra 字段](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)。

## 6. 联合索引与排序

对默认升序索引 `(a, b, c)`，固定 a 后，剩余记录按 b、c 排列，因此以下查询具备利用该索引顺序满足排序的条件：

```sql
SELECT id, a, b, c
FROM records
WHERE a = 1
ORDER BY b ASC, c ASC;
```

如果改成只按 c 排序，却没有固定 b，那么不同 b 分组中的 c 会重新开始排列，通常不能直接从索引顺序得到所需结果。固定 `a = 1 AND b = 10` 后再按 c 排序，则又有了相应顺序。

排序方向也要匹配。b、c 都升序时可以顺向扫描；都降序时可以反向扫描。若要求 b 升序、c 降序，普通的同向索引通常无法直接提供这个顺序，MySQL 8.0 可按需要设计混合升降序索引。

具备顺序条件，不代表优化器一定选择该索引；它还要比较过滤、回表等成本。出现 `Using filesort` 表示需要额外排序，不能据此断言已经写入磁盘或必然很慢。[ORDER BY 优化说明](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)。

## 7. 列顺序选择与使用边界

联合索引的列顺序决定哪些查询容易定位、哪些排序能被复用。设计时应先梳理主要查询的过滤条件、排序和返回列，再比较多个查询能否复用同一个前缀。

对于经常一起出现的等值条件，可以考虑放在前导部分，再结合范围和排序要求安排后续列。多个等值列谁先谁后，还要看其他查询是否只带其中某些条件，而不是只比较每个列单独的区分度。

例如查询总是同时约束 a、b 时，`(a, b, c)` 与 `(b, a, c)` 都可能服务该查询；如果另一类高频查询只约束 a，前一种通常更容易复用。低区分度的列也可能在组合过滤或排序前缀中发挥作用，不能仅凭它单独区分度低就排除。

增加索引列还会增加空间与写入维护成本。为覆盖少量查询把很多字段塞进同一个索引，可能得不偿失。已有 `(a, b)` 时，单列 `(a)` 可能冗余，但删除前还要检查唯一性语义、其他访问路径和成本。

最终应结合执行计划判断所用索引、访问方式、预计扫描量和 Extra 信息，再按需要观察实际执行。`key` 非空仅说明选择了索引；`key_len` 提供键前缀使用的线索，也不等于每个条件都同样有效地缩小了扫描范围。[联合索引的选择](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[执行计划字段](https://dev.mysql.com/doc/refman/8.0/en/explain-output.html)。

## 8. 知识小结

联合索引的基础是多列有序：先比较第一列，相同后再比较后续列。最左前缀、范围访问和索引排序，都可以从这个顺序推导。

记忆时抓住下面五点：

1. **最左前缀由索引列顺序决定。** WHERE 条件的书写顺序通常不改变它。
2. **范围定位与条件过滤分别判断。** 后续列不能继续收窄区间时，仍可能参与下推过滤或覆盖。
3. **覆盖与下推解决不同问题。** 覆盖提供查询所需列，下推提前排除无效候选项。
4. **利用索引排序需要满足顺序条件。** 前导列是否固定、排序列顺序和方向都要检查。
5. **索引选择还取决于成本。** 能使用某个索引，不代表一定选择它，也不代表实际代价足够小。

可以用一句话复述本章：**联合索引按多列组成的键排序；查询能否有效利用它，要分别分析查找区间、过滤条件、输出顺序和所需列。**
